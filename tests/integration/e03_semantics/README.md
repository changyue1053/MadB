# Finite C07 source semantics

This is the local `source-semantics-{ordinary,enhanced,disabled}@2` recipe using
`madb.composition/1` and `madb.profile/2`. It checks the existing 16-call C→ArkTS
source surface. The older `chain-*@1` five/eight-row observation remains unchanged.
The profile's HAR/API23 tuple is a fixed configuration intent, not evidence that
this check builds a HAR or runs an API23 application.

`inputs.py` assembles applicant claims and existing SDK source assets. It never
calls the host requirements function. The actual public reader emits checked IR;
the independent host derives requirements from that IR, fixed effective policy
and reviewed mechanism source bytes. Every normal call requires declaration,
ABI-lowering and ordinary facade projection. Async bridge, subscription, stop,
cancel, dispatch, drain and release rows apply only to the corresponding public
operation, instance anchor and mechanism layer. Release distinguishes provider
payload destruction, Core ticket retirement, native context and JavaScript
listener retirement. State/event anchors stay distinct. Optional wrappers add
ordinary receiver/ViewModel projection, stop and close handling, including the
actual ArkUI `snapshot` output. Auxiliary type declarations do not manufacture
runtime ownership rows.

Ordinary/disabled require exactly five assets, five direct dependencies and 95
responsibility rows. Enhanced requires seven assets, ten direct dependencies and
107 rows. Fixed mechanism bytes include input validation and frame layout as well
as the source files owning those responsibilities. Changing applicant bytes and
re-pinning the complete identity chain does not grant a new supported recipe.
Ordinary/disabled cannot smuggle optional source through renamed assets or frozen
input entries. This source recipe has no `physical-assembly` stage and refuses a
claim for that capability. It does not define new SDK lifecycle semantics.

`check.py` performs three actual reader→generator runs, checks independent public
handshakes, immutable complete IR transfer, raw process cleanup, one complete
Source commit and a source-only consumer. The negative matrix re-pins coherent
inputs and exercises the public metadata/semantic entry with declaration shapes
from the actual successful reader output. Those direct negative checks are not
counted as new declaration-reader executions. Two separate actual reader failures
also prove that semantic refusal prevents the generator and Source commit.
The raw results and identity inventories remain in the new output directory.
`--positives-only` explicitly runs a development subset.

Run with the repository's fixed Python and the same frozen build's three images:

```sh
.venv/bin/python -B tests/integration/e03_semantics/check.py \
  --output /absolute/new/output \
  --bridge /absolute/images/composition_generation_probe \
  --probe /absolute/images/composition_chain_probe \
  --peer /absolute/images/arkts_composition_peer \
  --observation /absolute/fixed/tool-observation.json
```

`adapters/contracts/tests/evolution.rs` separately exercises existing model/wire
version rejection, old reader isolation, byte/semantic identity separation and
all evidence freshness dimensions. `composition_semantics.rs` tests 23 refusal
branches through synthetic bound inputs; those fixtures are explicitly not C07
positive evidence. Neither suite grants execution or certification authority.

No check here claims native compilation, physical assembly, SDK/HAR delivery,
target lifecycle, alternate backend support, or whole-package acceptance.
