# Gobley Kotlin/Native adapter — C06

This profile uses published Gobley **0.3.7**, UniFFI **0.29.4**, Kotlin/Native **2.4.20**, coroutines **1.11.0** and its declared atomicfu **0.32.1** dependency. It targets `macos_arm64` / `aarch64-apple-darwin`, Release, macOS deployment target 14.0. The official Gobley Gradle plugin is not required: the pinned standalone generator runs before explicit cinterop/konanc tasks. No CPF/OHOS, Android, other Apple architecture or minimum-OS execution result is implied.

`toolchain.json` pins archives, generator dependency lock and both generator patches and both runtime patches. `driver.py install` compiles baseline and patched generators from the same source, applies patches before compilation, and records all original/patched runtime files. `verify_install` rejects missing, additional or changed runtime files and source symlinks. The host additionally freezes the receipt and compiler closure; a receipt is not a certification claim.

## Initialization and P03 corrections

The Native initializer checks the UniFFI contract version and every generated API checksum before registering callbacks or allocating business data. Expected values are emitted from the pinned generator's `ComponentInterface`; no hand-maintained symbol/checksum table exists. The managed header preserves Rust UInt8/16/32/64, handle and RustBuffer length/capacity signedness. Native wrappers explicitly convert to/from the shared Kotlin signed bit carriers at function, struct and callback edges. A Kotlin mask alone cannot repair a mismatched C declaration: LLVM may optimize using the declared signed range. The test-support scalar fixture verifies zero, the high bit and all bits set across all four unsigned widths in both call directions. `openEngine(expectedProfile)` is the ordinary checked entry, consistent with the JVM facade.

1. **Generator:** `ffi/Async.kt` separates calculation/conversion from outward completion. `native/CallbackInterfaceImpl.kt` lowers the result before completion ownership handoff. Notification exceptions increment a diagnostic counter; they cannot trigger a second completion or reclaim an already transferred value. A registered foreign-future job owns a lazy coroutine and its parent job; completion/free retains the existing Rust-owned cancellation protocol. Handle-map size is read under the existing lock. The native Rust-future cleanup scope surrounds IO dispatch, so a pre-cancelled caller cannot leak an eagerly created future before the dispatched body starts.
2. **Runtime:** UniFFI 0.29.4 queues a raw `ForeignFutureResult`, whose buffers have no automatic `Drop`. A dropped receiver otherwise loses late/unpolled result allocations. A private guard consumes abandoned results through the selected generated `LiftReturn` and drops the lifted owner; normal consumption takes the raw result and preserves the original lift thread. Cleanup catches callback-error panics after ownership consumption, so an unwind cannot cross the C callback frame. No public ABI/layout or raw-pointer `Send` implementation is added.

3. **Native future ownership:** polling retains an owned Rust value in a deferred lowering closure; only explicit `complete` converts and transfers it. Free/drop after READY releases the Rust value, and poll-panic status buffers have explicit cleanup. This closes cancellation between READY and complete without adding `LiftReturn` requirements or a new unsafe `Send` implementation.

The cleanup profile permits only generated, thread-independent lifts. Arbitrary custom converters, borrowed results and thread-affine cleanup are unsupported. Reverse async **Object** results remain unsupported on 0.29.4 because its raw Arc pointer representation is not `Send`; this is separate from supported forward Rust object handles, sync reverse callbacks and Rust async operations. Do not silently substitute a newer runtime or weaken pointer safety to admit that combination.

Production callbacks are the bounded engine's synchronous `Host`/`Sink` protocols. Reverse async `AsyncHost` and `TestLedger` are an explicitly separate `test-support` build used for P03; their invoking consumer owns completion and teardown acknowledgment, not `Engine.awaitClosed()`.

## Entry points

- `driver.py install --tools <cache>` — verified source installation; network/build action is explicit.
- `driver.py build --tools <cache> --output <target> --profile-digest <identity>` — patched runtime, independent SDK Cargo lock, Release. `--test-support` enables the separately identified probe binary.
- `driver.py generate-udl --tools <cache> --output <generated>` — production generation directly from the authoritative UDL; common/native/header bytes match library-mode output from the corresponding SDK.
- `driver.py generate --tools <cache> --library <dylib> --output <generated>` — common/native Kotlin and cinterop header. `--baseline` is regression-only.
- `native.compile_native(...)` — explicit compiler closure, three runtime KLIBs, header/dynamic library, target and deployment settings; creates a distributable bindings KLIB plus non-embedded cinterop KLIB or a real consumer executable. Production consumers link the selected `@rpath/libmadb_boundary_gobley.dylib`; swapped-library/profile rejection therefore tests the actual loaded library. Only the isolated P03 baseline comparison explicitly embeds a static library.
- `probe.py` — original generated code fails its exact double-completion assertion; patched generated code passes completion-failure, cancellation/late-resource and pre-handoff failure checks. Original runtime fails a real allocation-release assertion; patched runtime passes 12 combinations of allocated string, nested values, object owner and declared error across cancellation/normal orders. A second runtime regression proves that READY→free and abandoned panic buffers leak on the original source, then verifies normal-complete and abandoned String/object ownership on the patch. Logs and observations are inputs to the host's existing report format, not a new certification format.

The SDK wrapper shares its UDL and mapping source with `sdk/rust/uniffi` while using a separate manifest, lock, crate identity and UniFFI version. Metadata comes from the version-matched `madb-gobley-metadata` binary; the host never infers its structure from generated text.
