# C07 ArkTS 四路线实施与验收

任务 C07 · 规范基线 0.9 · 起点 MadB `2a0d992e75e5198985ee4e383ca19cfc1f48ee6c`、MadB-Lab `c53a64ef2c160fa7ca9b8e23d6365b84d882fc41`。当前是实施与准入记录，尚无 C07 整包验收结果；状态以[任务目录](../catalog/implementation-plan.json)为准。

## 范围与责任

四条直接路线为 `KN-ARKTS-NAPI`（CPF-KMP-CMP + akinterop）、`ARKTS-RUST-NAPI`（napi-ohos）、`ARKTS-C-NAPI`、`ARKTS-CPP-NAPI`（平台 Node-API）。CMP 渲染、KNOI、UniFFI-ArkTS beta、ANI 和工程初始化保持各自任务范围。

复用 C04 冻结端口、契约格式及候选清单，路线特例留在 generator/toolchain adapter；语言 SDK 承担声明的类型、所有权、异步和环境协议。Lab 从公开 HAR/库/声明构建独立 HAP，不导入生产者私有源码。设备安装和执行属于独立 Lab，不直接放入会预执行再重放的 C04 构建步骤。

每路线需要一个能力明确的完整 profile，而非实现所有语言类型。拟用小型值类型、显式资源、异步操作、取消、state/event 和非阻塞通知验证边界；不强制沿用 C06 的同步 Host.transform。不能通过把异步、观察或退出清理全标 Unsupported 绕过必需验收。具体 API、预算和 profile 在 P05/P06 探针后冻结。

## P05：已核对的 akinterop 源码风险

公网 `akinterop-runtime-ohosarm64:1.1.0` [源码包](https://maven.eazytec-cloud.com/nexus/repository/maven-public/org/cpf/kotlin/akinterop-runtime-ohosarm64/1.1.0/akinterop-runtime-ohosarm64-1.1.0-sources.jar) SHA-256 为 `faf4560347aaa4e9cef4cdc387b99b9fb3c472f3c1f07afb5a209a624a8138b8`，与参考工程本地副本相同。其 66 个 Kotlin 文件与[上游固定提交](https://gitcode.com/CPF-KMP-CMP/akinterop/tree/75ba50c77afda2845a3a6c51cdcddb03d4fd0ab8)逐字节相同。以下是源码事实及待验证影响，不冒称已在目标复现或证明发布二进制可复现。

| 已观察实现 | C07 必需处理 |
|---|---|
| ArkValue 强引用依赖 GC cleaner；NapiRefCleaner 使用全局无界 Channel、延迟批量 Main 线程清理 | 明确每 env 的引用 owner、容量、显式释放和退出前 drain；GC 不作为强关闭证明 |
| 部分普通回调使用全局主环境并同步等待；代理调用可在线程回投前转换参数 | 非阻塞通知必须先投递到所属 env，再做 N-API 转换/调用；不支持的同步跨线程回调明确拒绝 |
| legacy registry/init 与较新的 per-env registry 并存，部分注册失败路径缺回滚 | 验证实际命中路径；重复初始化、注册失败、多 env 支持范围分别检查 |
| native function.cpp 的 TSFN 队列参数为 0；callJS 无 env-null 清理分支；部分 sync=false 调用仍使用 blocking enqueue | 不能直接用作有界退出协议；补充受控排队、销毁时只做合法清理及在途载荷所有权，再实际复现 |
| Promise 的 scope.cancel 不等待 native 清理；tag 构建声明与发布 atomicfu 元数据存在差异 | 独立定义操作终态/结果接管/清理 ACK；解释并固定可复现构建配方和补丁身份 |

仅限制 main-env 不能消除引用延迟清理、无界队列和退出责任问题。任何修补都需来源/补丁摘要、重新生成与重编译、目标竞态验证；不能改版本说明来代替修复。

## P06：napi 与平台 Node-API

`napi-ohos`、derive、build、sys 四个 `1.2.0` 和 `ohrs 1.5.0` 均已分别查询公开注册元数据；它们独立锁定，不推导同号。napi 默认 feature 为 napi4，使用 async cleanup 需明确 napi8。

[napi 固定源码](https://github.com/ohos-rs/ohos-rs/blob/e4eb8e1b493d6c3aa98ca220776605963df8135a/crates/napi/src/env.rs)中的 async cleanup 包装，在用户闭包返回后即移除原生清理 handle。启动异步任务后立即返回不等于 drain；真正异步退出需显式持有原生 handle 至清理完成，或受管补丁，并验证无需等待已关闭的业务队列。

当前先用已有 Beta SDK 编译独立开发探针：C++ TSFN/Worker 清理、真实 C 调用、napi Rust 直连、无 CMP 的 CPF/akinterop 导出。使用专属测试 HAP，原始产物、日志与实际运行层级分别记录。这些探针不替代正式 SDK、完整 profile、Release/HAR 及独立 Lab 的整包验收。

## 正式环境复测结果

[最终基础预检](c07-formal-environment-observation.json)实际退出 0、errors 为空；显式目标仍为 API 23 Release Arm64 模拟器，certifies_c07 固定为 false。独立审查发现并修复了 JSON 重复键被后值覆盖、可能把 Beta 元数据误判为 Release 的问题；产品、组件和工具 package 元数据使用同一个局部严格读取器，8 个冲突反例纳入回归。

[基础机制实跑观察](c07-formal-basic-probe-observation.json)关联当前 nonce/PID 和 HAP 摘要：正式 SDK 26.0.0.105 编译、compatible API 23 / target API 26，在现有 API 23 目标实际执行 Kotlin/Rust 的空串、ASCII、中文、内嵌 NUL，真实 C checksum，以及 C++ 正常回调、异常、满队列和 Worker 退出。C++ 探针最终分配/释放 15488/15488、TSFN 5/5、活动线程/待释放载荷均为 0。**这些计数不代表 Kotlin/Rust/C 完整 SDK 的生命周期已通过。**平台 TSFN 配置容量 4、实际可排队 5 的差异保留，SDK 自有许可预算不能依赖平台队列参数推断。

Kotlin 采用显式双侧构建配方：native helper 使用正式 SDK N-API 头；cinterop/runtime 继续使用配套 CPF 平台头和预编译 klib。直接替换后出现的重复枚举类型失败已保留，未以业务强转掩盖；实际桥接子集的 49 项布局/签名比对相同。CPF shared linker 的 Scrt1.o 修正和受管 patch `24d1b30e…` 都是候选身份的一部分，不能宣称原版 akinterop/CPF 无修改通过。

合包还验证了同名运行库冲突：正式 SDK 的 libc++ 缺少受管 Kotlin 库要求的两个异常 ABI 符号，消费包明确只选择已核对的 CPF libc++，记录输入与打包后摘要，并实际装载四路线库；没有按文件复制顺序静默覆盖。该依赖闭包是本次组合的观察，不能推广到所有 CPF/SDK 版本。

当前收据来自 debug HAP 和社区 debug 签名；Release 混淆、HAR 独立消费、完整 profile 与主 env 清理继续分别验证。`.venv/bin/python scripts/check.py` 已完整退出 0，含 26 项环境预检、C05/C06 SDK 不变量、文档检查及隔离 DOM 单元测试；它不等于重新执行各目标候选或真实浏览器测试。本地源码/文档检查与目标探针不能代替远程 CI；本轮尚未启动 GitHub Actions。
