## 架构与角色复杂度判断

核心模型、规则、计划与端口不应依赖特定 UI 或运行时；宿主、生成器、工具链及打包适配器承担外部执行。抽查 Cargo 依赖、app ports/bootstrap、事务提交和 ArkTS 共享协议与该方向相符。C/C++/Rust 的 ArkTS 路线复用同一协议和原生 owner/worker，各 provider 独立；Kotlin 采用自己的受管路线，未因外观统一而要求共用第二套运行时。对应设计应保留，不能从接口一致推导线程、取消或释放自动正确。

| 角色 | 可以保留的简化 | 实际缺口及实施落点 |
|---|---|---|
| SDK 作者 | 单一结构声明、显式安全策略、复用既有后端生成器 | 目前固定 SampleEngine 包装不证明一般业务生成；L01 定义子集，L02–L06 实现，L07 用第二个独立业务模块增删改验证 |
| 应用消费者 | 普通 API、包内依赖、显式 owner，UI 只拥有自身观察 | I/L 的真实 IDE、生命周期及正式包仍未完整验收；不能要求消费者手写内部摘要、DAG 或补库 |
| 扩展作者 | 小型公开端口、清单与既有进程协议 | E01–E06 尚未整体落地；应以外部扩展和禁用/冲突负例验证，不再加一套注册框架或重复运行时 |
| 维护者 | 固定工具锁、受检构建批次、任务目录与生成视图 | 需要把未分配 CLI 和跨阶段出口落实到工作包；删除重复的状态文字比增加第二个看板更有价值 |
| 验证人员 | 独立 Lab、候选摘要、正反例与分层结果 | 保持 target-run/compiled/static、机制探针/普通候选/完整认证分离；不能按案例数量或子范围报告推算完成百分比 |

必要能力、配置增强、实验后端的设计边界总体明确：消费者不选 UI/Rx/CMP 时不传播对应依赖；项目已经承诺交付的配置仍须做完。X01/X02/X03/X07/X08 等保持自己的版本、目标和验收，不能借用相邻主线的发布资格。下一步优化应落在已有端口、生成器、初始化和验证闭环上，而不是增加更多库或层次。

### Runtime 高风险结论的第二意见

主审与两名独立审查者核对了 facade→最终 receipt→native registry 链路。ADR-0013 第66行允许最终 receipt 后复用槽，旧 gateway 探针也有真实目标重开相关观察（包括关闭尚未确认时拒绝重开），因此不能声称重开必然无意，更不能据此断言存在内存安全 bug。初始化失败后的重试、不同 env 使用退役槽、同 env 成功最终关闭后重开是三种不同能力。

已留存的普通 C 开发 HAR 目标消费者只初始化一次 Runtime，验证 Runtime 内 Engine 换代，最后重复幂等 Runtime.close；C++/Rust 使用同一消费者形状。旧 gateway 探针是正式 SDK26/API23 的真实目标结果，但其范围为私有完成机制，不能代替公开 profile、provider/worker 和完整候选的声明及验收。最终判断是“支持边界未闭合”。建议先明确首片是否正式支持重开：支持则增加能力声明和对应目标案例；不支持则另行安排准入实现修正。两种路径都不能通过删除限制、改写历史探针或只运行主机替身来完成。
