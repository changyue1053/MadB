# E01/E03 下步公共组合格式差异审查草案

仅提出新增格式的审查方案，未采用、未实现，不登记任务状态。依据当前工作副本的 architecture/17 §4–6、architecture/13、E01/E03/E02 acceptance，以及 extension-manifest/profile/lock/common/extension-wire schema；与 E02 作者核对过请求边界。Swift/ArkTS 既定选型、交付授权和责任分配继续有效，本次不重议。

## 现行格式与实质缺口

| 现有输入能表达 | 不能据此推导的组合保证 |
|---|---|
| manifest v1：包版本、组件/端口、路线/方向/目标、features、bindings；dependencies 仅 id/kind | 依赖的适用版本/目标/用途，以及同阶段不同组件的冲突；restrictions 文本不是可执行规则 |
| profile v1：具体 target/ABI/最低系统、工具版本/摘要、必需功能、defaults；backend_config 为受检后端私有配置引用 | 跨组件统一的选择、依赖作用域、四维唯一 owner；不能塞入可忽略 extensions 或交给单一适配器私解 |
| lock v1：profile 语义摘要/文件、工具精确版本、components(id/version/sha256)、inputs/schemas 字节清单 | “已固定这些文件”不等于验证依赖相容、普通/增强/替代/禁用，以及唯一物理装配 |

## 推荐最小差异：显式公共输入，有限配方

新增一个公共、闭合字段的 `madb.composition/1` 契约（名称待审），由 E01/E03 的共同 decoder/规则读取；初版只校验有限、人工维护的精确配方，不实现版本区间求解、任意表达式或自动换桥。最小内容：

- **选择/适用性**：配方 ID、基础路线、明确启用组件/集成、具体方向和目标条件；与 profile 精确一致，不展开目标笛卡尔积。普通、增强、替代后端、禁用各自是明确配方；关闭项不得仍被隐式拉入。
- **依赖边**：请求方→既有依赖身份，精确版本与来源/字节 pin 的引用、适用目标、用途（宿主工具/作者插件/消费编译/目标运行/可选集成/验证开发）及装配责任引用。相同依赖多用途逐项记录；实际字节复用 lock/候选文件清单，不另建包下载器。
- **责任声明**：`边界 + 规范 public_id 或受检 operation + 语义阶段 + 实例作用域 → 唯一 owner`。owner 解析到已选组件或其 SDK 资产；阶段沿 §5 的读取、ABI lowering、投影、async 桥、订阅、投递、取消/停止/排水/释放、物理装配。作用域是配方中有定义且能绑定到生成接线的实例/逻辑订阅范围，不能是自由文本标签或运行时私有句柄。首版用精确符号/操作，不引入通配规则语言。
- **前提/处理关系**：引用现存必需能力、明确互斥选择和阶段先后/输出 owner。真实受检 ContractIR 与所选配方生成“必须覆盖”的责任集合，再检查恰好一个 owner；不能让清单通过漏写必需阶段自证完整。缺失保证不凭组件自报补齐。

建议以新 `madb.profile/2` 显式引用该公共契约，保留独立的 backend_config。引用沿既有“FileRef + 语义摘要”模式：字节用于核验，确定性语义投影进入 profile/任务身份，避免 profile 与组合文件相互包含摘要形成环。组合文件只回指 profile ID/适用条件，摘要关系单向。当前 profile/1 是封闭且只有主版本标签的格式，不能静默给 `/1` 增加必需字段。旧 profile/1/锁继续走原路径，不强制批量迁移；新组合 profile 必须拒绝不认识该契约的读取器。公共 feature 的最终 ID、适用参与者与摘要投影随格式决定一起定稿，不预先写入核心功能目录。

首版可保持 manifest v1：它继续负责发现/身份/逻辑引用，有限配方承担新增的公共约束；不谎称 v1 dependencies 已获得新语义。lock v1 的 inputs/schemas/components 可继续绑定组合文件、schema 和精确组件；E01 校验新增关联及完整性。若审查发现这些既有锁字段仍缺身份事实，另列具体缺口再升锁版本，不先制造一套组合锁。

## E02 与兼容影响

**v1 控制帧可以保持**：组合根先完成受检解析，再生成既有 read/generate/build/verify/package 的单组件请求，每组件独立握手、固定输入输出域。公共 FileRef 已携带 schema/sha256/size；新增文件内容及 profile 解码能力需要演进，JSON Lines envelope、operation 和取消终态不需要改变。只把每个操作实际需要的功能发给对应参与者，不要求无关 compiler/helper 理解全组合或虚报能力。

E01 负责引用、依赖、精确锁和有限配方；E03 负责必需语义、责任覆盖/唯一性、冲突及失效；纯规则消费受检值，不访问 Registry/磁盘。E02 承接会话；I01 产生工程计划及既有任务引用；app/plan 编排，host 依既有 Source/Build/Candidate 事务决定最终提交。新增格式、默认选择或 owner 变化按真实依赖影响 profile/task/generation/candidate 身份；source 只在实际源输入清单或字节变化时改变，不重定义现行 source 摘要。旧候选原结论不改。schema、decoder、digest 投影、共同正反向量、未知版本/字段/功能拒绝必须同批交付，不能仅加入 JSON 文件。

## 最小正反例与退出

| 有限正例 | 必须拒绝的邻近反例 |
|---|---|
| 一个现有 C07 普通 profile；所有必需阶段各一 owner | 删除排水 owner；同一元组加入第二 async/订阅 owner；指向不存在 public_id |
| 同一普通 profile + L05 ArkUI V2，增强复用原订阅/内核 | 增强重复源订阅/内核装配；要求底层未支持的取消或跨 env 保证 |
| 禁用 ArkUI，普通 API 与候选闭包独立 | 未选项仍进入解析/下载、编译/链接或抬高最低系统；仅无 import 不能通过 |
| 一个已授权替代后端的独立设计 profile，单选一个桥 | 同符号同时选择 napi-ohos 与替代桥；目标/版本/pin 不匹配；借主线报告判其通过 |

先以受控配方/格式向量证明选择、责任、摘要和拒绝；再用实际可用普通+增强配置执行两组件及失败/取消不提交半批次，最后由独立 Lab 证明普通/增强/禁用消费。替代 profile 暂无产物时只记设计拒绝检查，运行证据保持缺失。两会话串联测试不能替代以上共同格式或 SDK 组合验收。需审的是新增公共组合契约/profile 引用、兼容拒绝与摘要规则，非已批准的扩展选型或开工授权。

## 交叉审查后的决定前提

决定前仍需精确定稿 composition 投影、集合排序、profile/2 摘要域和 feature 身份，并提供一个普通配置、一个增强配置的实际适用责任集合。不得把所有生命周期阶段机械套到每个同步符号。模板对 profile 采用明确版本准入；当前只认 /1，/2 必须随其决定与共同向量实现，未知版本拒绝。本文仍为待审草案，不表示 /2 已采用。
