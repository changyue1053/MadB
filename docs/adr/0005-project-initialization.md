# ADR 0005 工程初始化与原生 IDE 集成

状态：本方案采用；模板格式、平台工程生成器与 IDE 行为由 S0 至 S4 探针和消费测试验证。

## 背景

用户需要一次操作创建可以继续开发的跨端工程。只生成绑定文件或示例目录仍要求使用者配置构建顺序、native 制品、源码根和 IDE 入口，无法达到降低使用门槛的目标。

现有 MadB 设计已定义 `init`、规则、生成、构建与验证链，需要补齐工程创建用例及模板交付，而不是建设另一套 FFI 或运行时。

## 决策

1. 扩展单一 `madb init`：输入模板、平台和 profile，创建用户自己的应用或 SDK 工程。
2. 使用版本化声明式模板与模块配方，复用既有边界配置和任务图；ProjectPlan 与 ContractIR 分离。
3. 交付各平台原生 IDE 工程，专用 IDE 向导可选；原生工程导入和运行列入对应主线阶段的退出条件。
4. IDE 构建通过项目 Wrapper 和明确子任务更新绑定与 native 制品，避免依赖用户终端 PATH 和手动复制。
5. 区分结构、导入索引、构建、运行、调试证据；默认初始化验证构建，请求级别之外不填写通过。
6. 源树在同文件系统无覆盖提交；需依赖绝对路径的构建在最终目录执行。后续失败保留完整工程和诊断。
7. 首次交付文件与持续受管文件分离，用户业务和构建入口不被重生成覆盖；初始化不负责已有工程迁移。

## 考虑过的替代方案

| 方案 | 结论和原因 |
|---|---|
| 复制一个固定 Demo 仓库 | 不能准确选择模块、版本和目标，也缺少升级来源与验证闭环 |
| 只生成单一 VS Code 工作区 | 可以帮助导航，但不足以替代 Android、Apple、ArkTS 的原生运行链路 |
| 必须安装专用 IDE 插件才能创建或运行 | 增加使用与维护成本；向导应复用标准入口并作为可选增强 |
| 临时目录构建成功后整体移动 | 缓存和工程可能记录绝对路径，不能证明最终目录可用 |
| 为任意语言与平台自由排列模块 | 路线能力不能传递推导；只推荐验证过的配置，未知组合明确拒绝 |

## 结果与代价

开发者得到一次创建、正常 IDE 构建、源码变化自动生效的流程。工具需额外维护模板版本、工程格式适配、Wrapper、环境诊断及真实 IDE 验收。

模板代码归使用者继续开发；源码来源、工具版本和受管范围仍可追踪。系统 SDK、签名和设备前提继续明确呈现。独立 MadB-Lab 验证这些承诺，不由模板自身宣布通过。
