# MadB 核心模型与扩展语义演进

扩展性要求语言身份开放，同时保持安全语义受检。核心模型只表达跨边界必须一致理解的事实；语言语法、编译器细节与平台 API 留在适配器中。不能以“不修改核心”为理由丢弃所有权、线程或错误语义。

## 1 三类变化

| 变化 | 示例 | 处理位置 |
|---|---|---|
| 新语言对已有语义的实现 | 新语言的字符串复制、同步返回、显式关闭 | Generator、SDK、Toolchain 和相应测试 |
| 后端或运行时特定约束 | 当前环境才能调用某回调、某目标不支持零拷贝 | 能力限制、带来源的观察、适配器检查及 Lab 特例 |
| 当前模型无法表达的公共语义 | 现有所有权/隔离模型不足以定义一种新资源转移协议 | 新功能规范、IR 与规则版本、受影响后端适配 |

是否是公共语义取决于安全和可替换性，不以“至少两个语言已经需要”作为硬条件。单一语言出现的新机制也可能暴露核心模型缺口。反之，换一个注解名字不应新增核心类型。

## 2 开放身份与受控语义

LanguageId、RuntimeId、RouteId、ComponentId 是经过校验的开放标识。它们用于登记、选择与诊断，不承担行为定义。纯规则针对类型、生命周期、能力和观察运行，不按语言名字选择结论。

Type、Policy 及核心功能 ID 有明确版本和完备含义。新增枚举成员也可能破坏旧读取器；不能因为 JSON 仍能解析就视为向后兼容。协议容器、IR 类型和生成 SDK 的公开模型分别评估。

规范区分三种扩展数据：

| 类别 | 旧读取器行为 | 约束 |
|---|---|---|
| 非语义元数据 | 可忽略，但保留其原始工件以追溯 | 如展示标签；不得改变生成、检查或提交结论 |
| 后端配置与约束 | 必须由选定适配器解析和验证 | 未知配置键报错；有效值进入摘要与能力判定 |
| 必需语义功能 | 必须由核心规范及相关参与者认识 | 未知即阻断；不能降成注释或可选字段 |

带命名空间的 extensions 容器只允许第一类。第二类进入版本化适配器配置并受校验；第三类通过 required_features 显式协商。把线程限制放入可忽略元数据属于违规。

## 3 Lowering 与语义保留

每个转换应记录输入符号、原始类型、目标表示、有效策略、前置条件与所需运行时支持。它只能把已明确的语义转为后端可以表达的机制，不能凭类型名猜测业务行为。

例如，把一个 ID 值类投影为字符串可以由声明和规则机械完成；把一个共享可变对象投影为独立快照，则必须明确快照时间、读取执行器与更新方式。包装为目标语言的 Future 不会自动使阻塞调用变为非阻塞，也不会赋予取消底层工作的能力。

跨多段桥接时逐段检查：输入存活期覆盖消费窗口、释放器唯一、执行器约束可满足、错误分类不丢失、停止保证不减弱。两段都能编译不构成组合安全证明。

适配器输出的是带来源和精度的结构与观察，核心仍判断必需语义是否完整。启发式未发现问题不能转换为“线程安全”或“可以借用”的确定事实。

## 4 版本规则

| 变更 | 版本与兼容处置 |
|---|---|
| 文案、展示元数据、无行为影响的修正 | 更新相应文档或实现版本；有输出变化仍更新摘要 |
| 同一 major 下的新增结构或功能 | 升 minor，双方明确声明支持；不自动接受未知字段 |
| 类型含义、必需字段、终态或序列化表示改变 | 新 major；提供明确转换或拒绝旧版本 |
| 默认线程、关闭责任、取消效果改变 | 作为行为兼容变更审查，不以“签名没变”放行 |
| 修复导致此前被错误接受的接口被拒绝 | 标注安全/正确性修复及影响；更新工具和相关证据 |

扩展独立版本发布，不要求与 CLI、SDK 或 Lab 数字相同。协议可用也不等于后端、工具链及生成 SDK 兼容；这些身份仍由锁与真实消费验收固定。

自动转换只用于能证明语义等价的格式变换，必须保留来源与前后摘要。涉及未知语义、信息丢失或保证变弱时拒绝转换，提供显式配置或升级诊断。这里处理的是 MadB 自身后续版本演进，不引入旧 mad/MadDemo 工程迁移任务。

## 5 核心语义变更流程

1. 用最小边界案例指出现有 IR 无法表达的事实和具体风险，先写正反预期。
2. 提交 ADR，说明语义、状态转换、默认值、与既有功能的组合和拒绝条件。
3. 定义版本化字段和功能 ID，同步更新 schema、核心规则、诊断与文档；不能只增加字段而没有检查。
4. 给受影响参与者建立支持矩阵：读取器、规则、生成器、SDK、Verifier、缓存和包清单。
5. 更新支持该功能的后端，并让其他后端准确报 CapabilityUnsupported。
6. 在 Lab 验证新功能和受影响旧路线；改变公共默认值时回归所有受影响认证组合。
7. 发布工具、协议和扩展兼容说明；旧锁可复现旧组合，新组合重新产生证据。

不可靠的影响分析按保守范围使证据失效。只更新文档不应制造新运行证据；改变检查规则、映射、工具版本或语义后，不能沿用旧摘要的认证。

## 6 可扩展性与整洁代码约束

- 核心不 import 任何语言适配器、SDK 或编译器库；类型定义保持值对象，规则保持纯函数。
- 语言分支集中在适配器内；公共层按能力检查，不建立庞大的语言组合 switch。
- 类型映射采用显式、可独立测试的策略。规则顺序和前置条件可见，不用动态反射隐藏关键语义。
- Registry 只供组合根使用，依赖通过构造参数传入；单元测试可使用小型端口替身。
- 映射、状态机和关闭规则各有一个权威定义；生成代码不能成为其唯一规范。
- 对无法统一的线程或引用机制允许局部重复实现，通过共同契约测试保持一致，不抽象出虚假的共同能力。

这些约束分别落实依赖倒置、开闭原则、接口隔离与契约可替换性。共同契约不允许实现替换后悄悄减弱保证；必须选择一个能力不同的新 profile，并重新验证。

## 7 核心变更审查记录

每次因新语言修改核心时，PR 至少说明：缺失语义是什么、为什么现有字段不足、哪些旧功能受影响、旧读取器如何失败、缓存与证据何时失效，以及新增的独立测试。若理由只是方便调用某个编译器 API，应优先调整适配器。
