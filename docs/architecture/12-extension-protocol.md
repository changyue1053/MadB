# MadB 扩展进程协议与版本协商

扩展协议连接 MadB 宿主与独立适配器进程，承载契约读取、生成、构建、验证和打包任务。它是构建时控制协议，不规定 SDK 运行时采用 JSON，也不承担跨语言业务消息传输。

协议结构以[消息 schema](../schemas/extension-wire.schema.json)为准。本文进一步定义消息顺序、身份、版本选择、取消和提交规则；只通过 JSON 校验不代表协议有效。

## 1 传输与边界

初版采用 UTF-8 JSON Lines，经 stdin/stdout 通信，一行一帧；stderr 输出受限诊断日志。stdout 出现非协议文字、重复 JSON 键、超限帧或非法编码，宿主应终止该会话并报告 ProtocolInvalid，不尝试猜测修复。

每个进程会话同一时刻最多执行一个请求；宿主可用多个进程并行执行互不依赖的任务。实现不依赖多请求复用或动态库 ABI。第一方进程内实现也必须满足相同端口契约与验收，不因此获得更强的能力声明。

默认每帧最多 1 MiB、JSON 嵌套深度最多 32。握手超时、任务预算、终止宽限期和日志上限由宿主策略给出并记录。大模型、二进制与长报告通过相对路径、格式标识、大小和 SHA-256 引用传递，不放入控制帧。

文件引用必须位于宿主提供的工作目录：输入只读、输出只写受管 staging。路径禁止绝对位置、父目录跳转、符号链接或硬链接绕过和大小写冲突；解析前与打开时均检查。参数使用数组启动进程，不拼接 shell 命令。

## 2 版本分别管理

| 版本 | 控制的边界 | 处理规则 |
|---|---|---|
| 清单 schema | 包声明的字段结构 | 先解析，再决定是否允许启动 |
| bootstrap envelope | hello/reject 的基本格式 | 不认识则拒绝；不能先依赖尚未协商的业务协议 |
| protocol | 请求、结果和状态机 | 宿主与扩展选择明确声明的共同版本 |
| IR | 类型、策略、功能要求与语义 | 独立协商；同协议版本不代表同 IR |
| 扩展包和工具版本 | 实际实现及其依赖 | 由锁固定；握手不能自行升级 |
| 生成 SDK 版本 | 面向消费者的公开契约 | 单独评估 API、ABI 与行为兼容 |

protocol 和 IR 版本采用 major.minor。首次解析时分别选择双方显式列表中的最高共同版本，不把相同 major 的未声明 minor 自动视为兼容。frozen 执行必须使用锁中的组合；运行时不能因为发现新版本而重选。

相同 major 下仍必须协商 required_features。扩展声称支持某版本但不满足本次必需功能时拒绝执行。协议、IR、扩展和实际工具版本全部进入生成缓存与证据身份。

## 3 握手

宿主预先校验包和清单，再启动锁定入口。流程为：

```text
宿主 hello
  → 扩展 hello_ack 或 reject
  → 宿主校验身份、版本、功能与能力子集
  → invoke
  → result
  → 下一项 invoke 或关闭会话
```

hello 携带 session_id、期望扩展 ID/版本、component_id、manifest_digest、宿主协议和 IR 支持列表、本次 required_features。必需功能按该端口承担的任务选取，不能以整条路线功能的并集替代。宿主在 frozen 模式只提供锁中的版本组合。

hello_ack 回显 session_id、扩展及组件身份与清单摘要，返回选定 protocol、IR 与满足的功能。返回功能不得超出该组件声明，身份必须与启动对象一致，版本必须在 hello 与清单的共同集合内。握手只确认此次组件可执行请求，不给扩展授予全平台认证。

没有共同版本、身份错误或功能不足时返回 reject；尚无法发送合法 reject 时，宿主根据 EOF、退出码或超时产生工具错误。[会话示例](../examples/extensions/protocol-session.example.json)的 manifest_digest 按随附示例清单的实际字节计算；其他未随附 payload 的摘要和结果是示意值。清单摘要只校验内容一致性，不认证发布者身份，也不证明真实进程已执行。

## 4 请求与结果

invoke 包含唯一 request_id、组件身份、operation、协商版本、输入文件引用、相对 output_root 和 timeout_ms。operation 在初版限定 read、generate、build、verify、package；新增端口或操作要进行协议审查。

invoke 的组件必须等于本会话已经握手的组件，operation 必须对应清单中的端口。需要另一个组件时，由宿主建立它自己的会话；不能通过通用消息接口越权调用其他组件。

输入文件的具体 schema 由 operation 的端口契约决定：ReadRequest、GenerateRequest、BuildTask、VerifyRequest 或 PackageRequest。宿主与适配器都验证对应格式和输入摘要，不能把一个端口的 JSON 强制当成另一个。大文件引用不免除大小、路径和 schema 检查。

result 回显 session_id、request_id 与版本，终态为 ok、error 或 cancelled。ok 携带端口结果文件引用；error 携带结构化诊断；cancelled 表示本请求的执行和清理已完成且没有可提交结果。额外日志不是第二个结果。

控制协议 ok 只表示端口成功返回结果。例如 Verifier 正常产出 status=failed 的 VerificationResult，控制协议仍为 ok；宿主必须读取业务结果，不能凭进程退出码、ok 或文件存在发布 SDK。

每个请求只接收一个终态，未知请求 ID、重复终态、错误会话以及终态后写输出均视为协议违例。输出最终性由适配器先停止写入、再返回结果保证；宿主随后核对文件清单、摘要、格式和预期阶段。

## 5 状态机与取消竞态

| 当前状态 | 事件 | 下一状态与责任 |
|---|---|---|
| AwaitHello | 合法 hello | 协商，返回 ack 后进入 Ready |
| Ready | invoke | Running；占用一个 request_id |
| Running | result | 校验后 Finished；会话可再次进入 Ready |
| Running | cancel | Cancelling；停止派生工作并回收请求资源 |
| Cancelling | 正常结果或取消结果到达 | 结束执行；由宿主的取消记录决定不提交本请求输出 |
| 任意活动状态 | 崩溃、超时、协议违例 | Broken；隔离 staging 并清理进程树 |

cancel 引用当前 request_id，重复 cancel 幂等；它本身不是终态。宿主在发送取消前先原子记录“不再接收可提交结果”。如果结果已被宿主接受并完成该任务的终态判定，随后取消返回“任务已完成”，不撤销已完成阶段。

取消记录先于结果接受时，即使适配器因竞态返回 ok，输出也不能进入候选提交。适配器可已完成底层工作，但“停止等待”“停止进程”和 SDK 的“停止原生工作”是不同概念。该控制协议不改变生成 SDK 的取消契约。

适配器只有在派生工作结束、输出写入停止且请求资源已收尾后才能返回 cancelled。超过终止宽限期，宿主终止隔离进程树并记录 error/timeout；无法确认后台工作结束时保留清理缺口，不能伪造 cancelled。

崩溃或失联时外部执行状态可能未知，协议不提供 exactly-once 执行保证。重新尝试只针对具备明确可重放前提的任务，在新 staging 和新 request_id 中进行；没有自动重试提交、发布或不可逆操作。

## 6 诊断与故障隔离

| code | 含义 | 宿主动作 |
|---|---|---|
| ExtensionIdentityMismatch | 实际身份或清单摘要不符 | 拒绝执行并使本次结果无效 |
| ProtocolIncompatible | 协议或 IR 无共同版本 | 提示锁和双方支持范围 |
| CapabilityUnsupported | 本次必需功能缺失 | 生成前阻断，定位符号或配置 |
| ProtocolInvalid | 格式、顺序、请求身份或终态违例 | 关闭会话，保存受限诊断 |
| InputInvalid | 端口输入或摘要不符 | 不执行任务 |
| OutputInvalid | 越界路径、未声明文件或输出摘要不符 | 不提交 staging |
| ToolFailed | 编译器或外部工具失败 | 保留工具阶段、退出码和源位置 |
| ToolTimeout | 执行或清理超过预算 | 隔离、收尾并保留状态缺口 |

诊断保留 code、message、stage 和可选源位置，避免泄露环境变量值、凭证或业务内容。展示文本可本地化，code 稳定。

项目策略控制可用工具、工作目录、环境白名单和网络。清单申请的权限不能覆盖宿主限制。当前协议没有提供系统级沙箱保证，也不允许以“插件是独立进程”为由执行任意不可信包。

## 公共协议支持与作者职责

E02 提供可复用的帧编解码、严格解码、握手/终态驱动、取消接收、预算与结构化诊断支持，并以共同正反向量验证。扩展作者实现所需端口的输入转换、业务处理和结果封装，不从零复制一套协议状态机。E06 将这些公共接口和最小可运行模板交付给独立作者。

首先覆盖真实扩展使用的宿主语言；没有实际消费者时不为所有语言提前造一套框架。其他语言可以按同一协议和向量实现兼容端点；公共支持库是降低接入成本的手段，不是强制语言或进程形式。宿主始终独立检查权限、身份、输出及提交资格，不能因使用官方帮助库而跳过校验。

## 7 协议完成标准

实现必须通过版本交集、未知必需功能、身份伪造、畸形输入、超大消息、崩溃、重复结果、取消竞态、越界输出和派生进程清理测试。基础帧 schema 与示例在设计期可以验证；各端口 payload schema、状态机执行器及进程级测试属于 S0/S1 必需实现，不因示例能解析就视为完成。

## 尚未定义的端口不得借名执行

read/generate/build/verify/package 是当前控制操作的全部范围。远程存储、IDE 启动和诊断 sink 可以由宿主现有内部端口执行，但不因此成为第三方扩展协议操作。需要独立进程形式时，先定义对应 payload、权限、取消与兼容版本，再协商；不得把任意副作用包装成 package 或写入可忽略元数据。X09 承接存储扩展，I07 承接 IDE 向导。

## 多组件组合会话

[组合计划](17-extension-composition.md)由宿主解析并固定。不同组件分别完成身份协商，分别使用其端口 payload、独立 request_id 和输出域；不把另一组件的身份塞入现有会话，也不允许组件以 package 操作取得发布或任意服务权限。

宿主只将已经校验并冻结的上游结果作为下游输入。各步骤结果先独立验收，全部必需步骤及文件 owner 检查通过后，才按既有 Source/Build/Candidate 事务提交；控制帧 ok 不等于组合成功。任一必需步骤失败或组合取消时，禁止提交不完整组合，清理及保留诊断沿本协议与宿主事务执行。

需要新端口、公共组合语义或现有 payload 无法表达的信息时，先定义版本和共同向量，旧参与者拒绝未知必需内容；本节不扩展 v1 的操作集合，不把当前探针视为完整执行器。
