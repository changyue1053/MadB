# MadB 语言与后端扩展规范

MadB 以稳定的边界模型组织多语言工具，以适配器承接语言和平台差异。新增语言的正常变更范围是扩展清单、适配器、必要的 SDK 组件、模板和验证资产；只有出现现有模型无法表达的公共语义时，才演进核心模型。

本规范定义接入边界。跨多个组件、SDK 能力与工程资产的选择、组合、依赖和验收以[跨路线扩展组合](17-extension-composition.md)为准；本轮已授权的 Swift 与 ArkTS 扩展按该规范及对应 ADR 自主安排实施顺序，具体配置仍满足各自选择条件。进程交互见[扩展协议](12-extension-protocol.md)，公共语义变更见[模型演进](13-contract-evolution.md)，交付条件见[新增语言验收](../validation/05-language-onboarding.md)。它们属于设计基线，示例和实施授权不构成可安装扩展或认证记录。

## 1 扩展的对象

| 对象 | 身份与职责 | 不隐含的能力 |
|---|---|---|
| Language | 开放的语言标识，例如 dart、kotlin | 该语言全部语法都可导出 |
| Runtime | 语言执行环境，例如 dart-native、kotlin-jvm | 同语言其他运行时的内存与线程行为 |
| Route | provider、consumer、方向和桥接机制 | 与其他语言任意互调 |
| Profile | 路线加目标、功能、版本及运行时策略的确定配置 | 配置之外的平台或功能已经验证 |
| ExtensionPackage | 一组适配器及其声明、模板和必要 SDK 资产的交付单元 | 一个万能 Backend 或独立业务框架 |
| Certification | 某个固定配置与制品通过独立验收的记录 | 同语言、同后端的其他组合自动通过 |

provider 是公开能力的提供者，consumer 是调用者。consumer-to-provider 与 provider-to-host-callback 分别声明；支持回调不等于能导入任意消费端模块。

Language、Runtime、Route 使用开放标识，不在核心定义穷尽所有语言的枚举。核心的类型种类、所有权与取消语义仍由版本化规范约束，不能用任意字符串绕过检查。第一方保留 madb 命名空间；第三方使用受发布身份约束的命名空间。现有主线路线 ID 保持稳定，不因引入命名空间而重命名。它们是用户目录别名，例如 RUST-C-ABI；routes.json 的 protocol_route_id 明确映射到 madb.rust-c-abi。扩展清单只使用命名空间 ID，宿主解析别名后写入锁和协议；诊断可同时显示别名。禁止通过大小写猜测第三方 ID，禁止两个有效路线抢占同一别名。

## 2 模块边界与依赖

核心继续由 model、rules、plan 和 app 构成。外层通过下列小型端口组合，不增加同时负责解析、生成、构建和发布的 LanguagePlugin 基类。

| 端口 | 典型接入工作 | 允许复用 |
|---|---|---|
| ContractReader | 从权威元数据读取结构和来源精度 | 消费 C ABI 时复用 C 头读取器 |
| Generator | 映射类型、实现明确的语义 lowering、生成绑定和包装 | 调用现有生成器及公共输出检查 |
| Toolchain | 探测环境、构建目标、收集编译诊断 | 公共进程执行和任务调度 |
| Verifier | 运行探针或测试并返回观察 | 公共报告模型和 Lab 场景 |
| ArtifactPackager | 在临时目录组织语言包和原生制品 | 公共摘要、文件清单和许可检查 |

ArtifactPackager 只准备候选内容。ArtifactStore 由宿主控制，负责校验、原子提交和读取；扩展不能凭打包成功直接发布、修改认证结果或覆盖有效输出。

扩展之间通过公开端口和锁定的组件引用复用，不导入其他扩展的私有实现。组合根解析清单后构建局部依赖图；不把 Registry 暴露给所有业务对象，不在纯规则中查询插件或启动进程。

SDK 资产只在语言与路线需要时交付，分别采用相应语言的惯用 API。能复用后端已有资源机制时，不增加重复的句柄、引用计数器或线程池。新增消费语言不必新增该语言的源码解析器。

## 3 目录与交付单元

工具工程目录、端口位置和依赖约束以[最终工程骨架](02-modules-and-ports.md)为准；测试工程以[Lab 骨架](../validation/02-lab-architecture.md)为准。本规范只定义扩展的落点，不维护第二棵目录树。

| 扩展内容 | 落点与责任 |
|---|---|
| 声明、生成、构建、验证和打包实现 | 对应 adapters 分组；通过小型公开端口复用 |
| 编译器配套辅助工具 | helpers；独立版本和构建环境，不导入宿主私有对象 |
| 语言原语与便利层 | sdk 下按语言/能力组织；不依赖 CLI |
| 工程资产 | templates/projects 或 modules；可独立贡献纯模板包 |
| 交付组织 | extensions 清单及资产索引；不复制实现源码 |
| 宿主权限与最终提交 | app 的编排及 adapters/host 的实现；不向扩展授予最终存储或发布权限 |
| 真实符合性 | Lab 消费者、fixture、场景及独立预期 |

一个扩展包可组合多个现有组件；第一方可随 CLI 分发，第三方可独立仓库和版本发布。源码职责分组与实际 crate 不要求一一对应，实际构建成员由 manifest 登记。扩展之间不导入私有实现，App 不反向依赖某个扩展包。

扩展可用 `assets.kind=template` 携带[初始化资产](14-project-initialization.md)。纯模板包由模板目录独立分发；没有组件或路线时不伪造空端口。工程模板格式与扩展清单独立版本化，初始化不改变进程协议的操作集合。

## 4 扩展清单

机器结构以[清单 schema](../schemas/extension-manifest.schema.json)为准，[Dart FFI 示例](../examples/extensions/dart-ffi.extension.example.json)展示写法。JSON Schema 负责结构检查，组件引用、能力语义、路径和版本交集另由语义检查完成。

| 字段 | 含义与约束 |
|---|---|
| schema、id、version | 清单格式、扩展身份、独立版本；重复身份冲突报错 |
| compatibility | 明确支持的 protocol 和 IR 版本集合 |
| languages | 本包引入的语言和运行时身份；可以为空，表示仅为已有语言增加路线 |
| components | 导出的端口实现及其可处理功能；进程入口使用相对路径和参数数组 |
| dependencies | 所需扩展、工具链和生成器的逻辑身份；实际来源、版本、摘要必须写入项目锁 |
| routes | 提供方、消费方、方向、具体目标组合、功能集合、限制和组件绑定 |
| assets | 模板、SDK 资产与说明文件的包内位置；可以为空 |
| execution | 所需环境变量名和网络需求声明；不代表宿主已经授予权限 |
| extensions | 有命名空间的非语义元数据；不能承载隐藏的安全前提 |

示例中的 example=true 阻止它作为正式扩展安装。正式包不能把示例中的工具身份、路径或目标声明当成已验证数据。

清单没有 certified 或 testsPassed 字段。声明表示作者希望提供的能力，最终认证来自独立证据。路线目标采用具体元组列表，不能把 OS、架构、ABI 三个独立列表的笛卡尔积全部算作支持。

一个完整配置通常包含读取、生成、构建、验证与打包绑定；已有工件可使用经过声明的读取或校验适配器。不得用“无操作成功”绕过必要阶段。

components 与 routes 至少有一项非空：包可以只提供可复用组件，也可以只组合已有组件定义路线。组件功能按端口职责解释，例如生成器需要理解并保留相关语义，而纯构建器只接受构建输入；宿主不要求所有端口都重复声明整条路线的功能。路线的能力仍由完整计划与验证共同成立。

## 5 安装、选择与锁定

1. 用户配置明确选择扩展与路线。宿主不扫描项目里的任意可执行文件并自动运行。
2. 解析扩展包及传递依赖，核对发布来源、包摘要和身份；清单不内嵌自身整个归档的摘要，避免循环哈希。
3. 检查重复 ID、缺失组件、依赖环、端口类型不匹配、身份冲突和版本交集。
4. 将来源、包与清单摘要、工具实际版本、组件绑定、协议和 IR 选择写入项目锁。首次解析和更新使用既有 lock 流程。
5. 根据接口实际需求匹配路线能力。多条路线同时满足时要求明确 profile，不使用安装顺序或“第一个命中”决定语义。
6. 握手确认运行的组件与锁一致后执行计划。frozen 模式缺少锁项即失败，不临时下载或换后端。

第三方只能申请执行权限，宿主的项目策略决定实际范围。独立进程有助于依赖和故障隔离，不是操作系统安全沙箱；发布方信任、最小环境和受控工作目录仍然必要。

## 6 能力与路线组合

有效可用范围取接口需求、扩展声明、后端实际能力、目标约束和可用证据的交集。开发阶段可明确运行未认证的实验配置；正式发布只接受当前配置的必需证据。

核心功能使用带版本的 ID，例如 core.call.sync@1、core.resource.explicit-close@1；字段中的字符串只承担身份表达，是否认识该语义由核心功能目录决定。未知必需功能必须失败，不能由扩展把它改标为可选。

多个适配器可以在构建计划中组合，但 A→B 与 B→C 不能自动推导 A→C 已支持。组合路线必须明确定义两段之间的表示、所有权、线程、错误与关闭协议，并作为独立 profile 验证。任何中间序列化、额外复制或异步队列都要可见。

## 7 Dart 接入示例

以 Dart Native 消费 C ABI 为示例：复用 C 读取器，接入 dart:ffi 与 ffigen，生成惯用 Dart 包装，并增加 Dart 工具链、打包与真实消费验证。Dart 官方说明了 C API 调用和从头文件生成绑定的机制。[Dart C 互操作文档](https://dart.dev/interop/c-interop)

首个示例只声明同步调用、明确复制和值或显式关闭的资源。异步、流、宿主回调和其他运行时不在该示例能力内；申请这些能力时应被准确阻断。它们仍可通过后续扩展版本逐项加入，不因示例边界缩减 MadB 原有主线范围。

E04 的必需结果是通过公开扩展契约得到可独立消费的 Dart FFI 包及真实同步行为证据；build_runner、元数据注解和扩展方法按该配方需要选择，不要求把语言特性表中的每种技术全部启用。原型、正式集成和发布的设计深度按[定稿节点](../delivery/04-design-readiness-and-first-route.md)区分。

[ADR-0026](../adr/0026-dart-sync-extension-contract.md)已采用首个macOS Arm64同步包的普通API、单包装配/实际镜像核对、单isolate资源所有权与显式关闭契约。正式组件通过公开端口复用，受检同步视图保留原native身份；具体格式、类型/错误和拒绝边界以该决定绑定提案为准。采用契约不表示注册、生成链、独立包或目标验收已完成。

Rust 或 C++ 只有在明确提供相应 C ABI、原生适配及行为契约后才能复用这条消费机制。不能从 Dart→C 样例推导 Dart→任意 Rust/C++ API 或 Dart→Kotlin/Swift/ArkTS 已支持。

## 8 扩展性验收原则

新增一种现有 IR 可表达的消费语言时，model、rules、plan 不应增加语言判断。允许修改组合根的注册、清单、适配器、测试和文档。若必须修改核心，评审应指出缺失的公共语义及其受影响路线，并遵循模型演进规范。

新增语言的完成定义是“作者能交付受检 SDK、消费者能使用、维护者能独立验证”，不是只生成一个能编译的方法。完整验收条件由[新增语言接入与验收](../validation/05-language-onboarding.md)维护。
