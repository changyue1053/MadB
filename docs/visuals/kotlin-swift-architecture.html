      DEPENDENCY RULE · 按需进入消费端

      生成依赖与应用依赖分别管理

      • SDK 作者构建：Kotlin、Gradle、SKIE、可选 NC 插件、MadB 生成器、Xcode / Swift。
      • 应用运行：生成的 SDK、Kotlin runtime 和实际使用的桥接运行库；组合配置按需选择 NC Async / Combine / RxSwift 产品。
      • 普通消费者：通过预生成 SDK 使用方法、状态和资源接口；消费端便利宏另设可选依赖。
      • IDE：模板接入 Gradle 与 Xcode 构建任务，源码改动能触发必要重建；CLI 与 IDE 共享同一构建计划。
      DECLARATION / STREAM IDENTITY

      一份声明归属，一份流身份

      • 生成归属：源声明 → SKIE 或 NC → 生成符号 → 公开入口，记录可追溯映射；禁止同一入口双重异步包装。
      • 配对：初始值、状态 getter、Flow 与可选 Publisher 外观绑定同一源流、owner、scope 和共享策略。不能仅按属性名称判断同源。
      • 行为：重复读取属性不能意外创建新流；多个外观不自动共享一次收集。冷流、热流、重复订阅与取消目标分别验证。
      • 一致性：同一流身份不等于“读当前值＋订阅”原子完成；首值、重放、序号和竞争规则仍由契约明确。

      业务开发者看到的普通 API

      下例是 MadB 拟提供的消费外观，不是已经生成并编译通过的代码；具体名字由契约和后端导出结果确定。

      @MainActor
func observePage() async {
    do {
        for try await state in client.observeState() {
            guard !Task.isCancelled else { break }
            self.state = state
        }
    } catch is CancellationError {
        // 观察停止；共享引擎仍由业务 owner 管理
    } catch {
        self.error = error
    }
}
// SwiftUI .task / UIKit 页面观察 owner 管理本次任务。
// 需要排水确认时，再调用显式的停止确认 API。

      三种 NC 外观，共用同一导出能力

      • Async：单次调用使用 asyncFunction(for:)；流使用 asyncSequence(for:)。[NC]
      • Combine：单次调用与流分别包装成 Publisher；每次订阅都可能启动一次调用或收集。订阅 owner 保存取消令牌。[NC]
      • RxSwift：单次调用为 Single，流为 Observable；订阅与 dispose 由明确 owner 管理。[NC]
      • MadB 共同协议：把等待取消、停止观察、停止工作、业务撤销分开；保持一次终态、迟到结果清理和错误分类。
      同时提供多个 Swift 外观不等于共享执行。对有副作用的命令，重复订阅是否触发重复操作必须由契约明确。

      Swift → Kotlin：cinterop 类型要实际调用

      Kotlin API 若使用自定义 cinterop 类型，SKIE 需要知道提供该类型的 Framework。按声明配置 ClassInterop.CInteropFrameworkName，再编译并链接真实 Swift 调用；仅看到生成声明并不足够，未知 Framework 可能产生 unavailable 占位入口。

      • 编译探针：构造外部类型 → 调用 Kotlin 原始入口 → 调用 SKIE 增强入口；核对真实模块名、头文件、导入、链接和返回类型。
      • 失败处理：缺少映射或生成入口不可调用时，阻止该能力认证；不能把“原始入口可调用”当成“增强入口也通过”。

      SKIE cinterop 限制

      Kotlin → Swift：宿主协议单独验证

      Swift 实现导出的 Kotlin 协议或提供 ObjC 可见接口，再验证 Kotlin 侧能注册、调用和注销。SKIE 生成的纯 Swift 增强外观不能直接假定可被 Kotlin 反向导入。

      • 编译探针：检查实际 ObjC 导出头与 cinterop 可见声明，编译 Kotlin 调用点；Swift 宿主实现单独进行严格并发检查。
      • 运行探针：按约定执行器回调，覆盖完成、取消、重入与关闭排水。纯 Swift 泛型或 AsyncSequence 仍走显式适配。

      反向可见范围

      若此 SDK 同时装配 C++：普通 Swift 公开界面可通过 C / ObjC++ 包装隐藏 C++ 配置；受控工具链源码同建可选择 direct interop。另按“方向 × 构建系统”验证：SwiftPM 的 C++ → Swift API 消费不能默认视作支持；开启 C++ interop 也可能要求依赖目标同步开启。本页 Kotlin ↔ Swift 路线不自动获得这些跨路线能力。Swift 构建约束

      05所有权、线程与关闭协议

      语法糖调用同一套必要运行时；关闭日志与追踪时，正确性保护仍然生效。

      谁持有，谁关闭

      App / 业务 owner持有共享 Kotlin engine，决定初始化与最终关闭。
      Engine scope / 资源注册表管理后台任务、共享数据源、原生资源依赖。
      页面观察 owner持有 Task、Cancellable 或 Disposable；只管理本页观察。
      本次观察 / 操作实例上下文存活到停止协议完成；迟到结果有唯一回收方。

      取消一个页面对共享 StateFlow 的收集，不自动关闭共享上游。上游行为由共享策略、其他消费者和 engine owner 共同决定。[共享语义]

      关闭是状态转换，不是一个布尔值

      Open→Closing→Closed
      • Open → Closing：原子关闭新操作准入，发起停止与退订，保留在途任务所需资源。
      • Closing：等待可确认的任务收尾、回调排水、结果交接；按依赖顺序释放。
      • Closing → Closed：满足契约完成条件后确认。超时返回“尚未完成”，不能假报已关闭。
      • 失效：不可恢复故障按契约进入 Invalid，阻止后续使用并安排仍可执行的清理。

      requestStop 与 awaitStopped 是职责示意；Task.cancel()、cancel()、dispose() 本身不承诺 MadB 所需的全部排水确认。

      MainActor / 执行器

      UI 状态在声明的隔离域更新；耗时工作由 Kotlin 或原生执行策略安排。await 不保证后台执行。

      Sendable / 共享可变状态

      按实际类型与同步协议检查。禁止为了消除编译警告而无依据添加 @unchecked Sendable。

      ARC ＋ GC

      显式断开注册与回调强引用环；析构时间和线程不能代替业务关闭确认。[ARC / GC]

      重入与竞争

      持锁区不调用外部代码；回调内关闭不能等待自身完成。操作准入、停止、结果交接统一测试。
