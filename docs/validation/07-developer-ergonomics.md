# MadB 声明式导出与惯用 API 验收

本套件验证[语言特性与低门槛 API 设计](../architecture/15-developer-ergonomics.md)：简化语法之后，公开效果、资源后条件和排错能力保持一致。适用范围由语言、运行时、宏/处理器、框架、构建方式和目标平台共同确定。

## 1 验收分工

MadB 验证元数据提取、展开形状、来源映射、确定性和编译失败用例。MadB-Lab 使用候选 SDK、可选便利包和实际消费工程，独立验证状态、资源、取消及 IDE 体验。

普通 API、便利入口、诊断开启/关闭构成对照组。预期从公开契约制定，不能只比较两份相同生成器的输出。对照的公开语义一致不表示二进制、性能或线程调度必须相同。

## 设计进入集成的材料

对当前选择的注解、宏、属性封装器或装饰器，随对应 L 工作包提交：作者输入和预期展开、普通与便利两种消费用法、依赖及目标限制、来源诊断和适用 DX 实例。普通接口先贯通，便利层原型验证后收敛；不能只提交语法片段便认定可直接实施或已通过验收。定稿节点以[实施准入](../delivery/04-design-readiness-and-first-route.md)为准。

记录没有启用某项便利机制的理由与普通替代用法；未承诺的可选语法不必强行实例化，但该 profile 承诺的状态、资源、取消和 UI 行为继续验证。Dart 探针保持同步子集，L08 等后续扩展单独取得证据。缺少释放器的声明拒绝、静态属性的有限诊断和动态运行错误使用不同预期，不能互相代替。

### 独立业务与普通使用实例

DX-01/02/11 至少增加第二个独立业务模块，使用对应 profile 声明支持的类型和资源。通过公开导出声明与必要策略完成生成；新增方法、修改模型字段、重命名及删除导出后重新构建，由候选 SDK 消费。不能编辑 MadB 私有映射允许清单、固定 SampleEngine Facade 或生成文件来完成这个测试。新语义不在承诺子集内时应准确拒绝。

DX-01 的普通消费者不手填内部身份、不手包每个操作句柄、不安装 MadB CLI、不手工补 native 库。预期身份由生成/装配提供，故意混入错误 profile/版本仍被拒绝；高级互操作的存在不允许普通入口绕过必要保护。DX-05/08 继续验证页面停止与业务 owner 关闭分别完成。

这些实例由对应 L02–L06 随平台交付，L07 汇总，不等待最终收口才开始普通 API 验证。实际手工接线数、恢复步骤和独立作者可完成程度作为体验证据；不以生成代码行数或接口数量代替。

Swift 扩展按 [ADR-0015](../adr/0015-swift-extension-delivery.md)复用以下对照，不新增案例编号：

- DX-01/04/05/06/09：基础 API 与 Observation/选用 UI 配置分别消费；读取与视图重建不重复注册，状态快照与事件通道分别验证，共享源的一个观察者停止不影响另一观察者，停止确认后无迟到 UI 更新。

L04 可按目标与能力提交子范围，例如 macOS 上的 Observation 适配；其报告只覆盖实际 API 与目标，不据此标记 iOS/SwiftUI/UIKit、正式分发或 L04 整包通过。已承诺扩展的完整交付仍需对应 INIT/DX 和独立候选消费。

Swift Testing 可用于新单元与集成场景，XCTest 保留 UI、性能及已有测试；选择框架不改变案例预期，也不要求全面迁移。API diff 可使用锁定工具链支持的 `diagnose-api-breaking-changes` 或实际产物接口比较，必须先确认目标与产品覆盖。[Apple 测试分工](https://developer.apple.com/documentation/xcode/adding-tests-to-your-xcode-project)、[SwiftPM API 比较支持](https://github.com/swiftlang/swift-package-manager/pull/8857)

DX-12 的 ASan、TSan、UBSan 等按语言、目标和工具链能力选择；记录实际插桩范围，未插桩的预编译 native 库不能算已检查。TSan 在 iOS 等移动平台使用受支持模拟器，UBSan 不用于证明 Swift 代码本身安全；诊断构建不替代未插桩 Release，检测无报告也不证明全部资源时序。[Apple 诊断边界](https://developer.apple.com/documentation/xcode/diagnosing-memory-thread-and-crash-issues-early)

## 3 关键反例

- 给同一接口配置两份冲突的释放责任：应在作者声明处阻断，不能生成后随机选择。
- 反复执行状态 getter 或重建视图：底层注册次数不因读取和重建增长。
- 两个页面共享热流，关闭一个：另一个持续收到合法更新；最后关闭按实际共享策略验证。
- 原生任务在页面取消后返回资源：观察终止后不再投递给已停止消费者，资源按契约认领或回收。
- 取消期间清理 scope 已被取消：收尾仍有明确 owner，回调上下文不提前释放，不遗留无主任务。
- 关闭追踪并触发关闭后访问或错线程调用：该配置承诺的保护仍然有效。
- 将诊断导出器改成抛错或慢消费者：诊断失败有界处理，业务结果和安全状态机不被替换。
- ArkTS 普通数据对象未经构造就被断言为可观察类：不能作为成功接入用法进入示例模板。

## 4 后端特例

- SKIE custom cinterop 缺少 framework 来源时，选择补充可解析的 `CInteropFrameworkName` 或显式适配；lambda 泛型参数的限制同样产生清楚诊断。Lab 真实调用承诺接口，不能仅用 framework 编译成功判断。
- SKIE 的本机源码构建与跨机器二进制交付是不同消费情形；后者由发布模板显式启用可分发构建并做异机消费。
- SKIE 与 NativeCoroutines 组合按接口唯一协程桥验收；类型增强、Async/Combine/RxSwift 的依赖与取消协议分别说明，不让两个生成器重复负责同一接口。
- JNI 可生成的签名、注册、参数转换与 C++ 手写语义门面分开。错误定位应指向作者导出声明；不要求消费者手写 JNI 描述符或猜测 ClassLoader。
- Swift C++ interop 开关可能传播到消费依赖。模板明确 direct-source 或包装 profile，不能用隐藏编译开关制造“普通 Swift 包可随处消费”的假象。

这些特例使用既有 DX 编号及公共问题 ID，来源见[平台审查场景](04-problem-catalog.md)。

## 5 证据与阶段

记录 SDK、便利包、工具/宏、UI 框架、设备和语言版本；注明是静态检查、编译、IDE 观察还是目标运行证据。源码位置精度不足时明确标记，不能伪造准确行号。

S1 建立普通 API、声明读取和诊断开关基线；S2/S3 随 Kotlin、Swift、ArkTS 路线完成对应 DX 场景；S4 补齐 C/C++ 包装和属性检查；S5 完成推荐配置独立消费、IDE 和新人实验。可选深度插桩及编译器插件按扩展能力单独验收，不推迟基础正确性保护。
