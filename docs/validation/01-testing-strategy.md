# MadB 整体测试策略

测试目标是验证使用者拿到的 SDK 满足公开契约。生成器黄金文件、单语言单测和编译成功分别提供部分证据，最终还需要跨语言、目标运行时和真实制品消费。

## 测试分层

| 层次 | 所属工程 | 验证范围 |
|---|---|---|
| 核心单元 | MadB | IR、策略解析、规则、计划、诊断和确定性 |
| 适配器契约 | MadB | 外部工具协议、版本不兼容、错误解析、路径边界 |
| 生成与编译 | MadB 和 Lab | 输出形状、漂移、真实编译、错误类型阻断 |
| 跨语言行为 | MadB-Lab | 双向数据、错误、资源、异步与回调 |
| 目标与 UI | MadB-Lab | env、生命周期、主线程、装载和页面状态 |
| 语言开发体验 | MadB 和 MadB-Lab | 声明/宏来源诊断、普通与便利入口、共享状态、诊断开关对照 |
| 制品验收 | MadB-Lab | 干净环境从固定候选安装和运行 |

## 用例集合

每个适用问题至少有正确用法与不利条件用例。不利条件包括非法输入、失序、重复、取消、关闭、分配失败和后端错误。应被编译或工具阻止的用法以准确诊断为期望；应运行成功的安全路径以契约后条件为期望。

内存测试验证资源计数、配对释放及生命周期。适用环境增加 ASan/UBSan/TSan 等动态检查；工具不支持的目标如实记录，不将替代工具的结果自动升级为同等保证。纯 Rust 的 Miri 检查不代表任意外部 C/C++ 已被执行验证。

并发测试使用 barrier 或显式调度钩子构造关键交错。随机压力和 fuzz 补充输入及调度覆盖，种子和最小复现保存到回归集。避免用长 sleep 假装事件一定完成。

[DX 套件](07-developer-ergonomics.md)验证语言特性带来的便利不削弱协议。重点包括热流多收集者、属性读取无注册副作用、宏组合、取消后的异步清理、诊断开关一致性和错误定位；[INIT 套件](06-project-initialization.md)验证这些生成任务进入正常 IDE 构建。

## 覆盖定义

问题目录是公共语义覆盖的基准，源问题映射防止整理时遗漏平台特例。适用性按 problem × profile × target × direction 决定。每个排除项写明“不适用原因”，每个缺失项仍为缺口；不能靠缩小用例集合制造通过率。

“全部问题有方案”要求每个问题有明确处置；“全部测试通过”只对报告列出的配置和用例成立。产品认证需要其承诺范围的所有必需项通过。

## 平台配方与已知缺陷门禁

公共目录包含 48 个问题和 96 个基础组；AUD-001 至 AUD-010 关联相应平台场景，研究条目数不代表可执行测试数。上游已知缺陷、设计缺口、实验候选及已有设计待验证分开记录，来源见[审查映射](../catalog/source-coverage.json)。

- P03 必须检查实际生成器输出：受影响 foreign future 模板通过受控抛错复现双完成路径，再验证修复后的完成/交接/释放计数。仅替换 Rust runtime 或让普通 happy path 通过不解除门禁。
- Android 新 KMP 模块、独立 app、native AAR/jniLibs 和显式 host/device tests 形成真实消费闭环；任务存在但未运行不能记为测试通过。
- 官方/CPF 两个构建根各自发布根 metadata 和目标制品，Lab 从独立 GAV 消费并注入错坐标；不靠开发机项目依赖掩盖发布问题。
- SKIE 接口以真实 Swift 调用确认可用；可分发 framework 与本机构建分开测试。Swift C++ 进一步按构建系统、调用方向及包装形式分组。
- JNI 测试对照真实 JVM class 描述符并检查注册、混淆和反向入口，不能只比较两份生成文本。
- CPF 正式 SDK 组合和实验 UniFFI ArkTS 的设备运行均要求准确的目标证据；没有设备时仅构建的 smoke 保留为目标编译证据。

## 独立判定与变异验证

黄金文件不应是唯一 oracle。行为期望从契约编写，例如停止完成后无回调、资源最终释放一次、数值无损。通过故意删掉范围检查、提前释放 context、跳过停止准入等变异，确认相应测试会失败。变异只进入专用测试构建，不能进入发布包。

同时验证测试基础设施：被测程序崩溃、日志缺失、超时或设备失联要产生失败/错误，不得作为预期成功。负例限定期望错误类别、阶段和位置。

## 结果分类

| 执行结果 | 含义 | 对必需项的处理 |
|---|---|---|
| passed | 已执行并符合预期，包括准确阻断的负例 | 身份一致且证据有效才可计入 |
| failed | 已执行，公开后条件或明确预期未满足 | 阻断 |
| error | 工具、环境、超时或证据收集异常，无法得到可信判定 | 阻断；错误位置记录实际原因 |
| skipped | 按显式执行策略未运行，例如仅请求结构检查 | 不计入通过；必需项仍缺证据 |
| unsupported | 声明的能力或目标不受支持 | 不计入通过；与产品承诺冲突时阻断 |
| blocked | 前置检查或任务失败，当前项无法启动 | 阻断；链接阻塞它的任务 |

六类互斥，附 evidence_level、环境和制品身份。缺必需 SDK 时，预检是 error，其依赖任务是 blocked；不能改成 skipped 后放行。stale 是证据依赖已变化的汇总状态，不是第七种执行结果。未执行时没有伪造的执行结果，证据为 missing。

工作包进度、能力汇总和逐用例结果是不同层级；扩展进程 result.status 的 ok/error/cancelled 仅描述协议请求，ok 中返回的测试报告仍可能含 failed。预期负例必须准确匹配错误类别和阶段，泛化崩溃不算 passed。

本规范定义测试计划和格式。实际计数、覆盖率和性能数值由实现后的报告产生。

## 从公共问题到实际用例

96 个基础组是测试分类，不能当作 96 个已写完的可执行用例。复杂交错由[关键场景](08-critical-scenarios.md)补足前提、动作、断言与清理；每条路线另把不适用项和拒绝能力写进实例，避免所有路线只重复“合法输入正常返回”。

文档校验与产品测试各自有报告。文档门禁检查追溯、内容结构与生成一致性；浏览器布局/交互需真实浏览器结果，静态几何或 DOM 替身不等价。
