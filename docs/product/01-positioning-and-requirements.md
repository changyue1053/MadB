# MadB 产品定位与需求

MadB 的交付单位是一套可消费的跨端 SDK：类型化接口、必要的运行时、平台工程接入、版本信息、示例和验证证据。主要收益是减少重复接线和边界事故，使使用者通过普通语言 API 完成业务。

## 用户与责任

| 用户 | 使用方式 | 仍需负责的内容 |
|---|---|---|
| SDK 消费者 | 安装包、调用方法、观察状态、关闭自己拥有的资源 | 理解业务成功、取消和关闭的效果 |
| SDK 作者 | 选择导出面，补充线程、资源、错误等契约 | 领域模型、算法、原生同步与 unsafe 前提 |
| 新工程开发者 | 选择模板与目标，一次创建可在 IDE 中开发的跨端工程 | 应用业务、目标环境和自己的签名配置 |
| 平台维护者 | 维护后端配置、工具链、发布包和目标测试 | 平台接入、版本准入和交付证据 |
| MadB 贡献者 | 开发核心、适配器、生成器与通用运行时 | 可维护性、确定性、诊断质量和回归测试 |

## 产品范围

主线包括 Kotlin/Native ↔ Swift、Kotlin/Native ↔ ArkTS、Kotlin ↔ Rust、Swift ↔ Rust、ArkTS ↔ Rust、ArkTS ↔ C/C++、Swift ↔ C/C++、Kotlin ↔ C/C++、Rust ↔ C/C++。Kotlin/JVM 与 Kotlin/Native 分开配置；C 和 C++ 分开描述；反向宿主回调和任意模块直接导入分开认证。源码集成、二进制 SDK 分发以及 Xcode/SwiftPM 等构建方式也是不同配置，不能只按两门语言配对宣称支持。

边界能力覆盖类型与错误、内存、线程、异步、订阅、UI 生命周期、构建打包、兼容与故障定位。UI 集成提供观察和状态适配，不决定导航、认证、同步、重试和业务事务。

工程初始化同时交付最小应用或 SDK 外壳、共享模块、边界绑定、原生构建接线和 IDE 入口。示例界面用于验证真实调用，业务架构由使用者继续演进，详见[一键初始化](04-project-initialization.md)。

## 可追踪的产品要求

| 编号 | 要求 | 验收方式 |
|---|---|---|
| REQ-01 | 提供按语言组合和任务选择的模板 | 新用户按快速开始完成示例，不手写底层接线 |
| REQ-02 | 保留唯一的接口结构权威源 | 改名、删字段和签名变化会更新生成结果或产生定位准确的错误 |
| REQ-03 | 支持范围可查询且不能被猜测 | 不支持的目标、类型、构建方向和分发方式明确阻断；生成后不可调用的 API 不计为支持 |
| REQ-04 | 生成代码与原生库成套交付 | 替换错库、错绑定或错运行时时验证失败 |
| REQ-05 | 内存与异步协议执行一致 | 生命周期和可控交错用例通过，负例被识别 |
| REQ-06 | 提供语言惯用 API | 用户接口不暴露不必要的裸指针、env 或手写序列化 |
| REQ-07 | 生成安全、确定且可增量使用 | 重生成一致、手写文件不变、失败无半套有效产物 |
| REQ-08 | 每个主线问题都有可运行方案 | 问题目录与 Lab 用例无未解释的空缺 |
| REQ-09 | 发布版本可在干净环境消费 | 从候选包安装，不依赖作者工作区与私有缓存；官方/CPF 坐标、native 依赖和跨机器 framework 均按分发配置验证 |
| REQ-10 | 错误能够自助定位 | 报告含边界、符号、目标、原因和可操作建议 |
| REQ-11 | 对外开放、可贡献和可分发 | 许可、依赖、发布说明、贡献流程齐全 |
| REQ-12 | 性能退化可检测 | 受控环境记录端到端延迟、复制和内存基线 |
| REQ-13 | 一键创建可在原生 IDE 中开发的跨端工程 | 模板在干净环境创建、导入、构建和运行；修改共享代码后在 IDE 重建生效；失败可恢复且不覆盖用户文件 |
| REQ-14 | 用语言特性和自动诊断降低开发门槛 | 声明、宏、状态/异步/资源便利入口与普通 API 语义一致；诊断可定位源码；关闭诊断不关闭正确性保护 |

## 易用性的完成标准

提供三条旅程。SDK 消费者从示例依赖到第一次成功调用，不接触 FFI 实现；SDK 作者从导出声明到两个目标 SDK，主要填写无法推导的语义；新工程开发者一次创建应用，随后在对应 IDE 中修改、构建和运行，不手动复制原生库或接线。首次使用实验记录人工步骤、失败点、耗时中位数与高分位，先测基线再定公开承诺。SDK 下载和系统工具链安装时间单独统计。

默认值只用于已有安全依据的行为，如有界复制和普通值传递；未知的释放责任、线程能力和副作用不能靠默认值掩盖。高级路径允许显式适配器，同时保留诊断、版本与证据要求。

[语言体验设计](../architecture/15-developer-ergonomics.md)分开约束作者侧生成、消费侧 API 和诊断。普通预生成 SDK 不强制依赖 MadB 自定义编译插件；已选择的源代码包、Swift C++ interop 或可选宏所需的消费工具明确列出；属性读取不隐式注册订阅或阻塞调用；页面观察不拥有共享引擎的关闭责任。

## 两个工程的产品边界

MadB 内置单元测试并发布工具、后端接入包与运行时。MadB-Lab 独立维护消费工程、案例、测试执行与平台证据，通过公开产物接口与 MadB 配合。两者共享规范编号，不共享未经公开的内部实现。

初始化得到的应用或 SDK 归使用者维护，不增加第三个 MadB 产品工程；MadB-Lab 从候选工具实际生成新工程验证模板，不用一份长期修补的 Demo 冒充初始化结果。

完整范围按阶段实现；预览发布必须标明具体能力组合。正式主线版本的资格由[实施计划](../delivery/01-implementation-plan.md)和[发布门禁](../architecture/09-build-packaging-release.md)共同确定。

实现门禁与风险验证分别追踪，见[决策与风险](../delivery/03-decisions-and-risks.md)。UniFFI ArkTS beta 为实验候选，不改变十六条主线或当前未实现、未认证状态。
