# MadB 实施计划与阶段退出条件

交付独立 MadB 与 MadB-Lab，九组语言边界、十六条主线全部保留。阶段安排表示验收顺序；人员和设备未落实前不编造日历工期。当前实施与认证状态以[工作包目录](../catalog/implementation-plan.json)为准。

## 计划的维护入口

目录维护 41 个工作包：30 个主线、11 个后续扩展。任务的责任、依赖、acceptance、文档及实际证据只在目录修改；[HTML 计划](../visuals/implementation-progress.html)直接生成阅读视图。本文解释阶段和交付安排，避免维护第二份任务明细。

目录中的 `decision_gates` 对应 [ADR-0009](../adr/0009-implementation-contracts-and-gates.md) 的 DEC-01 至 DEC-12，记录完成时点、规范、任务和验收。它们不是新增工作包，也不按“决策已写入”计工程完成度。

设计基线 0.9 的 Swift 必要能力采用 [ADR-0014](../adr/0014-swift-production-baseline.md)，九项扩展的选型与执行范围采用 [ADR-0015](../adr/0015-swift-extension-delivery.md)。ArkTS 十二项必要能力采用 [ADR-0016](../adr/0016-arkts-production-baseline.md)，十二项扩展采用 [ADR-0017](../adr/0017-arkts-extension-delivery.md)。讨论序号复用既有 DEC、问题、INIT/DX/CRIT 与工作包，不新增任务、案例组、阶段或完成率。

## 扩展设计与实施时点

依据 [ADR-0012](../adr/0012-extension-composition-and-delivery.md)，全部路线使用同一[扩展组合与接入要求](../architecture/17-extension-composition.md)。项目所有者决定实施授权；目录中的 phase、start_phase 和 depends_on 表达技术与整体验收关系，设计采用或候选库可用本身不构成开工授权，已授权范围不要求逐项重复确认。

本次已明确授权按既定结论推进 Swift 扩展，由技术执行方安排具体顺序。L01 的 Swift 契约及 L04 的普通观察/Observation 首个实现子范围已启动，与 C07 独立并行；其他已选 Swift 配置按下文交付顺序推进。ArkTS 本轮选定范围也已获实施授权，L01 的 ArkTS 契约与 L05 的普通观察/ArkUI V2 首片同步启动；C07 保持既有范围和验收要求。

E01–E06 继续是主线扩展机制；I/L 的基础与按配置增强、X 系列及 I07/L08 保留既有归属。Swift UI/薄宏归 L04，Kotlin Combine/Rx 的 NativeCoroutines 正式组合归 X01，Swift export 归 X02；ArkTS 普通观察/ArkUI 与按配置便利层归 L05，工程归 I05；UniFFI ArkTS、KNOI、ANI 分别归 X07、X08、X03。L08 深度改写不纳入默认交付。延期、未执行与缺失证据仍保留未完成，普通配置通过不能覆盖增强配置。具体子范围与实测证据在对应任务或 PR 留痕，不增设平行状态或排期系统。

## Agent 开发的计划执行

全部工作包遵循[Agent 开发规范](../engineering/07-agent-development.md)。每次任务在现有任务、Issue 或 PR 中明确编号及子范围、相关设计依据、修改边界和验收方式，再实施、验证、交付；不另建任务协议或进度系统。

范围内实现由 Agent 自主推进；改变既定架构或契约先形成具体变更并按现有流程决策。文档、计划冲突只暂停受影响部分；已经明确授权的调整无需重复确认。子范围完成不提升整个工作包状态，未执行和缺证据不计通过。

C01 建立两工程的简短根 AGENTS.md、真实检查入口及合入约束，并复用一个实际小任务验证执行流程；各平台门禁随对应工作包补齐。这是协作基线的一部分，不新增工作包或全量测试前置。

## 每项交付的完成标准

工作包提交问题/需求 ID、契约变化、具体输入输出、生成/手写分工、失败行为、适用案例、文档及兼容影响。后端交付包含 Reader/映射、生成接入、Toolchain、语言 API、Verifier 和独立消费，不能仅提交模板字符串。

- 准入决定已落实为格式、接口、任务图或明确的 profile 配方，并有正反例。
- 生成可再生、事务提交与输入追踪可靠；源码/产物/候选身份一致，手写文件保留。
- 适用的公开 API、资源/线程/取消、CRIT、INIT 与 DX 检查通过；未插桩 Release 独立验证。
- 报告绑定真实候选、工具、目标、Lab revision 和清理结果；缺环境、skip 或 unsupported 不代替必需项通过。
- 推荐模板可在原生 IDE 导入、构建、运行及修改后重建；承诺调试时另有断点证据。
- 发布候选包含依赖/许可/符号/来源，公共安装下载的是相同候选；生成模板和 runtime 的修复分别核对。

任务只有 `implemented + passed + 有效证据` 才计入验收。工作包数不是工时百分比；浏览器草稿、文档检查和图示不产生认证。预览可以交付明确子集；S5 完整版本需要每条主线的最低完整配置及全部适用必需项，变更承诺必须通过 ADR。

| 子范围 | 归属 | 可审查的交付点 |
|---|---|---|

## C07 后的并行执行与交接

采用一个主协调任务管理集成，按就绪情况委派子任务并行实施。实施负责人决定每批的任务数量、分工和集成次序；项目所有者负责新增范围及公共契约等实质决定。默认在同一协调任务内使用子 agent，保持一个决策和交付入口；确有长期独立交付需要时，再组织独立工作线程。工作线是职责队列，实际并发数量由接口、文件边界及机器/设备资源决定。

### 分工、集成与验证

每个并行子任务沿用工程规范的四项记录：工作包/子范围、输入版本、允许修改的文件或模块、实际验收。代码实施优先使用独立分支/工作树；在共享目录工作时，写入范围必须互不重叠。子任务基于固定提交和契约开发，接入新公共修改后复核受影响结果。

公共 schema/IR、端口、共享 runtime、工具锁、导出入口及任务目录在每批指定一个修改负责人。其他子任务提出所需差异，由负责人统一处理；同一文件需要多人修改时串行集成。构建输出按任务隔离；修改同一工具缓存、使用同一设备/模拟器或其他独占资源的步骤由主协调任务安排，避免并行覆盖。

主协调任务先集成公共契约和基础实现，再接入依赖它们的平台/模板改动，最后验证固定集成候选。子任务检查证明各自子范围，合并后仍执行受影响的跨包、生成、依赖闭包及独立消费检查。高风险所有权/生命周期/并发改动按既有门禁独立复核；源码变更后重新绑定候选与证据。

只有满足工作包完整验收才更新目录状态，随后重新生成视图。实现、编译、目标运行、独立验收和发布继续分别记录；未解决项在既有工作包/PR/报告中留存。文档整理、子 agent 完成或合并成功本身不产生认证。
