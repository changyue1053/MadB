# MadB 设计定稿节点与首链实施资产

MadB 可以在 S0 开始仓库、协议实现、原型和工具链探针。正式集成需要所用契约和可执行设计已经收敛，公开发布需要明确 API 及兼容承诺；无需提前冻结所有语言的便利语法。

本规范定义首链资产和集成准入，十二项实施决定见 [ADR-0009](../adr/0009-implementation-contracts-and-gates.md)。工作包状态以[实施目录](../catalog/implementation-plan.json)为准，语言机制与启用范围以[语言特性设计](../architecture/15-developer-ergonomics.md)为准。

## C01 的开始与完成

当前文档允许开始 C01。仓库/文档归属、环境锁、负责人、协作与 CI、公开许可按[实施计划](01-implementation-plan.md)的 C01 处理表落实；这些是建仓交付，不要求在编写第一个 Cargo manifest 前已有完整产品。

本地构建和检查通过不等于 C01 全体验收：远程合入约束与公开前提保留独立结果。完整 IR/payload/ABI 属于 C02，P01/P02 属于 C03；P03/P05 及 Swift、ArkTS 配套按对应配置阻断，不升级为 C01 全局前置。

## 设计定稿的四个节点

| 节点 | 必须确定 | 允许继续探索 | 对应工作 |
|---|---|---|---|
| 开始 S0 | 产品范围、语义权威源、模块责任、所有权/线程/取消不变量、探针假设与失败预期 | 接口名称、展开形状、具体工具配套及实现细节 | C01–C03、L01；协议和模板工作可同时开展 |
| 首链进入正式集成 | 本次 profile、输入声明、ABI 形状、端口 payload、错误与资源协议、工具锁、消费样例和正反用例定义 | 与首链无关的语言 API；首链内部实现可继续迭代 | C02/C03 的前置交付，C04/C05 集成 |
| 各语言能力进入集成 | 普通 API、语义映射、依赖和目标明确；便利层有等价普通用法及可编译原型 | 自定义宏/属性封装器的名字和参数可根据原型修订；不能静默改变关闭或取消语义 | L03–L06；相关路线及 DX 验收 |
| 对外发布 | 公共声明、默认行为、支持范围、依赖、兼容策略及真实消费证据形成版本基线 | 后续按版本演进新增能力或调整接口 | C10/C11、L07；扩展独立验收 |

实验不等于正式集成。原型进入独立实验目录或候选配置，记录假设、版本和结果；正式生成器、SDK 与模板采用评审后的契约。不要求用一个尚未实现的完整 MadB 工具先完成全部探针，也不能把手写探针成功当成生成流水线通过。

冻结表示建立可追溯的版本基线，不是永远不能修改。公共语义改变按[模型演进](../architecture/13-contract-evolution.md)处理，相关生成代码、消费样例、预期和证据同步更新。已发布的实验 API 同样需要说明兼容政策。

## 设计覆盖与实施就绪的区别

| 层次 | 应能回答 | 不能替代 |
|---|---|---|
| 架构覆盖 | 用什么机制、归哪个模块、有哪些约束及验收组 | 输入输出已经逐字段确定 |
| 可实施设计 | 当前配置接受哪些声明、生成什么、错误如何定位、谁持有和关闭、如何验证 | 实现已经正确、制品已经可用 |
| 实现与验收 | 实际生成/编译/调用结果、独立预期、候选身份及清理结果 | 其他目标或配置自动通过 |

当前语言特性表提供架构覆盖。具体可实施设计在对应工作包交付；尚未生成的代码、未运行的样例或伪代码不得被登记成验证证据。具体实现状态继续使用实施目录的统一枚举。

## Rust 与 C 首链的两条直接路径

首链使用 `RUST-C-ABI`，以 macOS Arm64 的直接双向消费为执行起点；目标、第二布局探针及冻结条件见[技术栈规范](../architecture/16-technology-stack-and-versions.md)。

| 路径 | 作者输入与手写责任 | 工具产物 | 独立消费者 |
|---|---|---|---|
| C 消费 Rust | Rust 的 C 可见导出实现及补充契约；符号、布局、释放和 panic 边界正确存在 | cbindgen 头文件，MadB 的受检包装/构建与候选清单 | C 程序只使用候选头文件和库 |
| Rust 消费 C | C 头文件、C 实现与行为契约；外部对象和回调安全前提明确 | bindgen 底层声明，按契约生成或接入的安全包装 | Rust 程序通过公开包与 C 库调用 |

cbindgen 生成声明，不自动实现 Rust 导出函数；bindgen 生成底层声明，不自动证明任意指针安全。两条直接路径分别验证，不能用一次 C→Rust→C 回调冒充 Rust 独立消费 C。工具职责以[后端规范](../architecture/06-backend-profiles.md)为准。

S0/P02 仍按原探针要求比较两种目标布局；至少一个真实目标执行双向调用。仅编译或布局观察的其他目标保留对应证据层级，不因此认证为运行通过。

| 资产 | 最小内容 | S0 前置与 S1 交付 | 责任工作包 |

| 生成接口与差异基线 | C 头、Rust 导入声明、包装形状、符号和布局检查；手写和生成文件分开 | S0 用锁定上游工具取得可编译的预期形状；S1 验证 MadB 实际生成、重生成和失败恢复 | C03、C04、C05 |
| 首链端口与诊断样本 | 用到的请求/结果字段、错误类别、缺元数据、错类型、错签名、取消与提交边界 | S0 字段契约、schema/正反样本和来源定位规则可执行；S1 实际端口行为符合协议 | C02、E01/E02 的适用部分、C04 |
| 固定 profile 与工具锁 | 宿主/目标/ABI、Rust/Clang/libclang、bindgen/cbindgen、编译/链接参数、来源和摘要 | S0 探针可复现并固定本次组合；S1 通过同一锁构建与再生成，不另选一套版本 | C03、C04、C10 |
| 消费者、fixture 和预期 | C 与 Rust 的真实消费者；资源计数、barrier、故障输入与独立 oracle | S0 给出可运行探针及详细验收定义；S1 Lab 消费候选包，执行下表正反用例 | C05、C09 |

这六类资产复用既有测试、fixture、expected 和候选目录。`C09/C10` 从 S1 开始提供首链所需的验证与打包；其 S5 阶段是全矩阵收口，不要求 C05 等待两项整体完成，不新增依赖环。

## 首链的最小验收范围

| 场景 | 成功路径 | 负例或可控交错 | 独立预期 |
|---|---|---|---|
| 双向数据与错误 | 标量、空值/空缓冲、字符串/字节与声明的错误正常传递 | 非法范围、编码或缺少必要元数据；错签名/布局在规定阶段拒绝 | 值与长度来自预先定义的输入；错误类别、阶段和来源位置准确 |
| 资源与释放 | 创建、借用、转移及配对释放按契约执行 | 缺释放器、输入失败后的收尾、关闭与在途操作交错 | 每项转移资源只有一个接管/清理方；原生工作存活时不提前释放 |
| 回调与停止 | 明确 function/context 的持有、线程与允许重入；注册和停止有后条件 | 同步首回调、注册失败、源端已取走 context 后并发停止；有队列的配置另测排队后停止 | 停止确认后不再进入消费者；context 在最后一次可能访问前保持有效 |
| 生成与构建 | 普通输入可重生成、编译、链接 | 生成中断、声明变更、工具不匹配、缓存错身份 | 旧有效输出保留；来源和诊断可定位；修改声明后绑定参与重建 |
| 公开包与诊断 | 两个独立消费者只用公开候选接口；Release 正常运行 | 缺库/错库、诊断关闭、sink 失败 | 错制品准确拒绝；诊断不改变业务结果或关闭协议 |

复用 48 个公共问题、96 个基础组和 [CRIT-01 至 CRIT-12](../validation/08-critical-scenarios.md)，按 profile 实例化。首链不必实现所有语言的 Flow、Promise 或 UI，但明确申请未支持能力必须被拒绝。异步停止/排水不能因为尚无高级语言 async 外观而省略；其等待形式由本次 C ABI 契约定义。

负例优先验证安全拒绝；需要注入真实不安全行为时放入隔离测试构建。不得对已释放裸指针随意调用后期待通用包装“自动识别”，也不把任意崩溃算作预期通过。

## 语言便利层的实施顺序

普通 API 和必要运行协议先贯通，再实现已选择的便利层。每个自定义宏、属性封装器或装饰器提供一个对照：作者输入/展开结果、普通用法/便利用法、依赖与目标限制、失败诊断和适用 DX 用例。

例如 Swift：先验证普通订阅、执行器投递、停止确认及资源清理，再让 Observation 模型接收本地状态；自定义属性封装器若启用，只包装同一公开 API。`@State` 或 `@Observable` 的存在不能作为订阅和关闭已正确实现的证据。Kotlin 同样先确定 native 观察如何连接 Flow，再复用 Compose 生命周期收集。

自定义便利组件保留在 L03–L06 的设计范围；是否进入一个具体模板由需求和实验决定。没有启用某组件，不得用“可选”跳过该模板已承诺的状态、资源或取消能力。S6 的 L08/X01 等扩展单独验收，不阻塞普通 API 首链。

## 准入决定的交付方式

首链正式集成前落实 DEC-01 至 DEC-06，以及首链涉及的 DEC-07/08/10/11；组合和公开分发再落实 DEC-09/12 的相应部分。一次决定的完成证明包含规则、具体接口/格式或任务图、成功用例和准确失败用例。仅增加一条“支持安全关闭”的说明不满足准入。

每份首链资产引用输入/工具/profile 摘要和归属工作包。C09/C10 的 S1 子交付证据随 C05 候选保存，其 S5 整体状态继续等待全矩阵，不新增第二套进度统计。平台 profile 必须提供机制责任表、队列/载荷预算、匹配检查及解析后的必需用例，不能直接使用展示页的配置名发布。

## 首链资产与源码骨架

首链的声明、模型/格式、应用流程、双向接线、候选及初始化资产按[源码落点](../architecture/02-modules-and-ports.md)归属实施；消费者、fixture、交错与预期按[Lab 骨架](../validation/02-lab-architecture.md)分开维护。C01 的可编译骨架与依赖检查只证明工程结构；C04/C05 仍需实际生成、错误/资源协议及独立候选消费证据。首链资产不得依赖临时目录或 MadDemo 私有代码。

## C02 已形成的可执行输入

字段和语义投影以[格式 v1](../schemas/README.md)为准，声明与关闭后条件以[首链 ABI 设计](../examples/first-route/README.md)为准。共同向量及领域反例进入仓库检查；它们使用合成配置，只证明格式/规则和本机声明编译。C03 用真实工具与独立探针接续这些输入，结果见下节；C05 才能形成独立 Lab 的完整原生运行证据。后续工作不得把这些前置样本直接改标为认证输出。

## C03 的 S0 资产交接

六类资产的实物、复现步骤、运行层级和剩余交付见 [C03 验收](../reviews/2026-10-24-c03-native-probes.md)。现在已有上游真实生成形状、四个 stateless profile 与既有格式锁、独立双向运行和签名/布局负例。C02 的完整 engine 声明已编译，资源/回调/关闭没有被改成同步子集承诺。
