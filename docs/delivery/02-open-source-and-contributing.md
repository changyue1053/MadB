# MadB 开源交付与贡献方案

目标是使外部开发者能够了解支持范围、安装使用、复现问题和提交改进。公开仓库中的说明不依赖作者本机路径、私有账号或未公开构建组件。

## 对外文件

发布前在两个工程根目录提供 README、LICENSE、CHANGELOG、CONTRIBUTING、SECURITY、必要的第三方通知及 Issue/PR 模板。用户文档提供中文主说明及英文快速开始，错误码保持稳定，叙述文本可以本地化。

DEC-12 的设计默认采用 Apache-2.0 覆盖项目自有工具、运行时、模板和示例；C01 在首次公开代码前落实 LICENSE、NOTICE、贡献来源与第三方权利核对。第三方原有许可保持不变，生成器嵌入片段单独登记；本文是项目设计决定，不代替实际 LICENSE。[GitHub 许可说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)

## 快速开始的要求

明确安装条件、当前可用版本、平台限制和一个成功调用。提供可下载包或锁定源码构建方式；没有发布包时页面使用“构建预览”措辞，不放虚构下载地址或让用户执行未存在的安装命令。

每个解决方案页包含场景、配置、调用方式、运行指令、预期结果和问题链接。按“使用 SDK”“制作 SDK”“添加后端”划分路径，深层原理不成为使用前提。

## 贡献流程

问题反馈记录版本、目标、最小代码、实际/预期结果及脱敏日志。贡献者先选择问题编号，修改契约时提供 ADR 或现有决策修订。PR 包含行为说明、测试和文档变更；禁止只更新 golden 来掩盖未解释的差异。

新增后端必须提交能力声明、限制、构建锁、正反例和真实消费证据。维护者无法获得目标设备时能力可保持实验状态，但不得出现在认证矩阵中。

新语言和第三方组件按[扩展规范](../architecture/11-language-extension.md)与[接入验收](../validation/05-language-onboarding.md)贡献。扩展包独立版本化；命名空间、来源、兼容组合和维护责任明确。不得通过私有核心接口、未校验的元数据或自报通过状态绕过公共协议。

GitHub 支持贡献指南、安全报告说明及 Issue/PR 模板，具体组织方式遵循其社区文件机制。[官方说明](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file)

使用 Agent 的贡献沿用[Agent 开发规范](../engineering/07-agent-development.md)：绑定现有任务和依据，报告实际验证与未完成项。两工程的根 AGENTS.md 在 C01 建仓时提供短入口；规范与命令须能从独立检出或固定版本的公开资料定位。Agent 生成的代码采用同一评审标准，不增加独立认证或自动发布权限。

## 安全与依赖处理

只记录复现所需的最小数据。安全报告通过私密渠道接收，修复后发布受影响版本、处置方式和测试。构建依赖锁定来源和摘要，外部拉取请求的 CI 不获得发布凭证。

自动生成依赖清单并记录第三方版本、来源和许可证；发布包提供校验摘要和可核对的构建来源。官方发布必须验证预期仓库与发布工作流的构建来源；各渠道的包签名按渠道要求配置，不能以“生成了摘要”代替来源真实性。

维护上游补丁时发布原始来源、固定提交、补丁摘要、许可证、回归用例与退出补丁的条件。生成模板和运行依赖分别记录；版本号相同的修改版不能伪装成未修改上游制品。正式下载必须包含重生成所需的受管补丁，不依赖维护者本机修改。

官方 Kotlin 与 CPF 首版 SDK 采用独立发布坐标。公开快速开始和初始化模板负责依赖映射，消费者不需要手工拼接平台 klib；下载页按消费者运行时与制品形态列出安装入口。详细配方见[发布架构](../architecture/09-build-packaging-release.md)。

## 历史参考与公开内容

旧项目仅作为工程经验来源。公开案例使用重新构造的通用 fixture，不直接搬运业务数据、私有配置或未经核对许可的代码。参考原文中存在的本机路径是历史定位信息；正式用户手册使用本项目内的可运行案例和相对链接。

公开仓库由 C01 建立：MadB 与 MadB-Lab 分别维护构建和贡献入口；实际 LICENSE、CI 和安装资产完成后才能给出可安装软件的使用说明。

## 初始化和进度的公开入口

首次使用文档同时提供“消费 SDK、创建 SDK、一键创建 IDE 工程、贡献扩展”四条路径；每条都由独立消费者复现。架构和进度 HTML 从版本化目录生成，公开页不得把本地草稿或规划状态显示为认证。设计资料可发布并评审；产品安装指南仅对已经交付的候选生效。

## 安装、升级与维护责任

首个公开分发渠道采用项目所有者控制的 GitHub Releases，发布明确版本的宿主资产、文件摘要和构建来源证明；包管理渠道复用同一候选字节或登记可追溯的封装过程。C01 固定真实组织/仓库和包命名空间，C10 核对发布工作流身份及下载后的安装结果；未取得的命名空间保持未配置，不能编造公开下载地址。

首次安装从已确认的项目仓库获取固定 release 及验证信息，受管下载限定该渠道与声明的依赖来源。Wrapper 固定版本、来源和摘要，不执行 `latest` 脚本，也不从未通过身份检查的下载结果执行工具。构建证明、传输保护与字节摘要职责不同；校验失败终止，不用同一不可信响应中的摘要证明发布者身份。验证配方绑定预期仓库、工作流和制品摘要；离线分发同时携带证明及独立维护的信任材料。[GitHub 来源证明](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations)、[离线验证](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/verify-attestations-offline)。

普通构建与 frozen 模式不升级。显式升级先展示工具、插件、SDK、语义和锁的变化，验证适用配置后提交新锁；失败保留旧锁和批次，不能偷偷回退成更弱语义。模板交给用户的文件不由工具版本升级覆盖。

发布维护者负责候选批准、渠道身份和坏版本处置；平台维护者负责受影响 profile；验证维护者核对证据。发现坏版本时停止推荐、标记受影响组合并发布处置说明，不覆盖同版本资产。历史摘要和证据保留；回退只选择已验证兼容版本，不自动下载执行新版本。C10 在 S1 的本地候选无需远程发布凭证，公开渠道门禁在发布前落实。
