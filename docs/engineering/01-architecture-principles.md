# MadB 架构设计原则

原则用于约束具体设计，必须能回答“防止什么变化风险、在哪里执行、怎样检查”。下列规则比模式名称或目录数量更重要。

| 原则 | MadB 中的落点 | 验证方式 |
|---|---|---|
| 单一职责 SRP | 读取、规则判断、生成、执行、报告分别变化 | 模块评审和依赖检查 |
| 依赖倒置 DIP | 核心依赖契约，应用组合具体适配器 | 禁止核心导入后端包 |
| 接口隔离 ISP | Reader、Generator、Verifier 按职责拆分 | 实现不被迫提供无用方法 |
| 开闭原则 OCP | 已有语义的新后端通过注册和能力声明接入；新公共语义显式演进模型 | 普通语言接入不增加核心语言分支 |
| 可替换性 LSP | 同一契约下的替换满足相同保证；保证不同则登记新 profile | 同一符合性套件验证，不静默降级 |
| 高内聚与信息隐藏 | unsafe、环境引用和编译器细节封装在明确模块 | 公共接口不泄露实现句柄 |
| 单一权威源 | 结构与策略各有唯一来源，生成物可追溯 | 漂移和来源校验 |
| 显式生命周期 | owner、借用、关闭、排水和释放分开 | 状态机及交错测试 |
| 组合优于继承 | 使用小型策略与适配器组合后端 | 避免多层平台继承树 |
| 纯核心与副作用隔离 | 相同快照输入产生相同计划和诊断 | 确定性测试 |
| 最小充分设计 | 先形成实际变化点，再引入抽象 | ADR 记录用途和代价 |

DRY 针对重复知识，不要求相似代码立即合并。两种平台看似相同、语义不同的清理流程可以分别实现，共享符合性测试。KISS/YAGNI 用于控制实现复杂度，不删除已经确定的产品范围。

## 设计审查问题

- 该模块拥有什么状态和资源，谁可以关闭它们？
- 哪些输入来自外部，哪些结果已经由编译器或设备验证？
- 新平台加入时需要改哪些公共模块，原因是否合理？
- 能否只用值输入验证规则，而不启动编译器或模拟器？
- 异常、取消、关闭是否仍能保留接口的后条件？
- 用户是否需要理解某个内部实现细节才能正确使用公共 API？
- 默认后端是否适合该运行时、调用方向、交付形态与构建系统，而不仅是支持同一语言对？
- 工具的稳定发布、生成模板修复和实际可消费制品是否分别核对，是否存在仅升级 runtime 却留下旧模板的问题？

## 架构与领域的边界

MadB 的领域是边界契约、能力、生成与验证。账户、聊天会话、同步状态和业务重试属于消费者。领域名字不能因为参考案例来自 MadDemo 就渗入通用核心。

Rust 作为核心实现语言不表示所有运行时也用 Rust。Kotlin/Swift/ArkTS 的生命周期与 UI 接入遵循其生态，公共语义通过规范与测试统一。

新增语言按[扩展规范](../architecture/11-language-extension.md)接入。开放语言身份与受控语义分离，不为每种语言添加核心枚举分支，也不把未知安全前提塞入不受检查的通用属性。

## 例外治理

确有必要违反默认原则时，ADR 记录约束、替代方案、代价、测试证据与重新评估条件。性能理由必须有测量；紧急修复留下可追踪的后续任务。例外不能把已知不安全行为描述为安全能力。

## 原则的源码归属

实际源码边界以[工程骨架](../architecture/02-modules-and-ports.md)维护：应用拥有端口，CLI bootstrap 是组合根，host 实现受控副作用，语言 SDK 管理其运行时协议，Lab 通过公开候选独立验证。逻辑目录与物理 crate 分开决策；依赖倒置依靠实际构建依赖、可见性和负例检查落实，不能只靠目录命名。
